**Legacy-auth-type resolution (SDK):** an identified+authenticated merchant consumer with no OAuth claims ⇒ `LegacyAuthTypePrivate` (`helpers.go:111-131`). The public `/v1/payouts` group accepts `{private, proxy, privilege}` (`payout_routes.go:23-25`).

**Can request-body `merchant_id` / `account_number` influence identity?**
- **Body `merchant_id`:** On the public create path, **NO**. `CreatePayoutToFundAccount` unconditionally overwrites `params.MerchantID` with the passport-derived id when context is non-empty (`core.go:415-418`); with a kong-minted merchant passport the context is always non-empty. The body `merchant_id` (DTO field `binding:"required,len=14"`, `dtos/payoutCreate.go:17`) must be present for validation but is discarded for identity. The only regime where body `merchant_id` is trusted is a **passport-less internal route** (context empty ⇒ no overwrite) — those routes are 404 at the hardened edge (§2). This is exactly the V20 / M3.1-second-campaign result: body-merchant trust is denied on the merchant edge.
- **Body `account_number`:** does not set identity, but it **selects the balance within the caller's own merchant scope** — `GetBankingAccountByAccountNumberAndMerchantID(ctx, params.AccountNumber, merchantID)` always passes the derived `merchantID` (`core.go:4818,4921,1305`). So account_number cannot reach another tenant's balance on this path. **Exception:** `translate_account_number_to_balance_id` uses the **body** `MerchantID` (`dtos/translate_account_number_to_balance_id.go:14`, `core.go:443,484 FetchBalanceEntity(ctx, params.MerchantID, params.AccountNumber)`) with no context overwrite in that core func — but that route is **not registered on any inbound router group** and is 404 at the edge (see §6, and the live 404 observed in both second-campaign runs).

**Where payouts rejects/ignores mismatches (cite):** identity mismatch is not an explicit "reject"; it is *ignored* — the body value is overwritten (`core.go:415-418, 553-557`) and DB access is filtered by the derived id (`repo.go:150-162`). A cross-tenant fetch/cancel therefore returns `RecordNotFound`→ public "The id provided does not exist" (400/404), proven by V20 (`test_v20_tenant_isolation.py:39-54`).

**Distinguishing the three denial sources** (critical for M4 tests):
- **Broker denial** (RED_LOOP allow-list): response is a broker JSON stub `{"error":"boundary_violation","detail":…}` with **no HTTP status** field and it is logged as `boundary_violation` / `violation_count++` (`broker.py:106-116`, `_validate_path:61-76`). Never reaches kong-lite. Applies to `/_arena`, `/twirp/`, `/metrics`, `/debug`, and any path not under `ATTACKER_ALLOWED_PREFIXES`.
- **Gateway denial** (kong-lite hardened): HTTP **404** with body `{"error":"no_route","detail":"no merchant route for path","path":…}` (`server.py:242-244`). Occurs **before** auth, so a valid or invalid key yields the same 404; no `WWW-Authenticate` header; no upstream trace/log on payouts-api. This is the fingerprint that separates "route not exposed" from "auth failed."
- **Service denial** (payouts middleware): if a request does reach payouts-api and fails auth → HTTP **401** with `WWW-Authenticate: Basic realm="Authorization Required"` and body describing invalid key/secret (`auth.go:110-168`); if it passes auth but is cross-tenant → **400/404** "The id provided does not exist" (repo filter, `repo.go:150-162`). A payouts access log line is emitted upstream.

So: **404 no_route = gateway**, **401 WWW-Authenticate = service auth**, **400/404 "id does not exist" = service tenant-scope**, **boundary_violation (no status) = broker**.

## 3. Service credentials & what kong-lite does with merchant-supplied ones

Service Basic-Auth identities exist in `arena.toml [auth]` (`arena.toml:114-155`): `api` (cred.API, secret `auth_api_payouts`), `fts` (`auth_fts_payouts`), `rzp_live` (workflow, `auth_workflow_payouts`), `fast_cron`, `merchant_configuration`, `xperience`, `vp_user` (vendorpayments), `banking_accounts_user`, `x_balances` (`auth_xbalances_payouts`), `settlements`, `irctc`. Monolith→payouts uses `[api.auth] rzp_live:auth_monolith_shared`. Secrets live in `ENV2_COMPOSE/secrets/auth_*.txt` and are mounted to payouts, **never to kong-lite** (kong-lite mounts only `secrets-kong` = merchant keys + passport private key + `auth_api_payouts`, `docker-compose.yml:1579-1590`).

| Service credential | Where used | kong-lite behaviour if a **merchant** presents it |
|---|---|---|
| `cred.API` (`api:auth_api_payouts`) | kong-lite injects it upstream for public payouts routes | The merchant's own `Authorization` is **stripped and replaced** (`server.py:268-287`). A merchant *cannot* set it — kong overwrites. Even if forwarded to a denied route, that route is 404 before auth. |
| `cred.FTS` (FTS→payouts `/v1/notify`), `cred.Workflow`, `cred.XBalances`, `cred.FastCron`, etc. | payouts internal groups | The routes are **404 at the hardened edge**, so the credential never reaches payouts. In frozen mode the route is reachable but the merchant key ≠ the service username, so payouts BasicAuth returns 401 (`auth.go:171-178` `isClientAllowed` matches by username; merchant key `rzp_live_ARENAM…` is not a configured service username). |
| Merchant sends `X-Service-Name` / `X-Task-Id` / `X-Payout-Actor-*` headers | — | Forwarded (kong strips only host/content-length/authorization + identity headers). But payouts derives merchant from the **passport**, and actor/app-name is taken from **passport consumer.Meta**, not these headers (`auth/headers.go:11-25`, `auth/passport.go:33-44`). Header-supplied actor cannot elevate. `x-merchant-id`/`x-entity-id` are additionally stripped by kong hardened (`route_policy.py:70`) and, even if present, lose to the passport (`authHelper.go:20-22`). |
| Merchant sends a **forged** `X-Passport-JWT-V1` | — | Broker strips any `x-passport*` header (`broker.py:85-86`); kong mints its own and sets it (last-writer-wins in the forwarded dict, `server.py:283`). If a forged token did reach payouts, it fails signature/kid validation: SDK requires RS256 + a `kid` present in the configured key set (`arena-passport-1`/`apiv1`) and `token.Valid` (`handler.go:54-72`). **No HS256/shared-secret fallback exists** (verifier `helpers/passport.py:6-9` documents this). |

**Does payouts check issuer/signature?** Signature + `kid` + expiry: **yes** (`handler.go:43-72`). Issuer (`iss`) claim: the SDK validates signature/kid/exp and the payouts middleware checks auth-type support; there is **no explicit `iss` allow-list check** in the payouts middleware path inspected — trust is anchored on the `kid`→public-key binding (`passport.edge identifier="arena-passport-1"` in `arena.toml:448-450`). Worth noting as a fidelity point, not an exploit (forging requires the private key).

## 4. Sub-merchant / partner header `X-Razorpay-Account`

- **Monolith semantics:** `X-Razorpay-Account` (`RequestHeader::X_RAZORPAY_ACCOUNT`, value `acc_<id>`) is the partner/linked-account selector. In `BasicAuth.php` it is read in `fetchAccountId()` (`:751`) and only honored under **partner auth** (`isPartnerAuth`), where it sets the sub-merchant scope via `checkAndSetPartnerMerchantScope()` (`:2619-2666`). For ordinary private (merchant-key) auth, passing `account_id` in the **body** is rejected for non-whitelisted merchants (`:946-969`, `BAD_REQUEST_ACCOUNT_ID_IN_BODY`). So the account header is meaningful only for partner API keys; a plain merchant cannot use it to act as another account.
- **Payouts service:** does **not** read `X-Razorpay-Account` anywhere (grep of `internal/**` returns no hits). The only place the twin touches it is the **workflow-sim** callback substitute, which echoes it from the payout's `owner_id` (`ENV2_COMPOSE/substitutes/workflow-sim/server.py:156-162`). So in the twin the header is inert on the create/fetch path — merchant identity is purely the passport consumer.
- **kong-lite / broker:** kong-lite and access-policy explicitly **preserve** `x-razorpay-account` (`access-policy.json:19,23`; `merchant-gateway-routes.json` preserved_client_headers) "so genuine authorization behaviour remains testable," and the broker forwards it (`broker.py:9-12`). **The twin therefore exposes the header but payouts ignores it** — a real partner-scoping test cannot be reproduced (monolith ingress missing).

## 7. Contradictions with earlier docs

1. **`translate_account_number_to_balance_id` is listed as an endpoint** in `payout_routes.go:96-101` (inside the `payoutRoutes` group) yet **has no route-policy entry** and returns 404 live. Reconciliation: it is declared in the Go route slice but the path form (`"translate_account_number_to_balance_id"` — note: no leading slash) is not exposed by the hardened classifier and its live 404 matches "default deny." Not a contradiction in behaviour, but the route table in `merchant-gateway-routes.json` omits it entirely; a reader could wrongly assume it is a public route. **Flag: document it as an explicitly-denied public-group member.**
2. **`payout_routes.go` includes `internal_contact_payout` and `payouts_internal` POST endpoints in the same `/v1/payouts` group that carries merchant passport auth** (`:48-59`) — i.e., the internal-app create shares the merchant group's middleware. The classifier fail-closes these to 404 (`route_policy.py:39`), which is safe, but contradicts any assumption that "everything in the passport group is merchant-safe." The `access-policy.json:75` note acknowledges this ("Source places it in a passport group, but its semantics are internal-app; fail closed").
3. **Frozen baseline is the compose default (`=0`)** while all M3/M3.1 acceptance and the M4 baseline run assume hardened (`=1`). Anyone booting via plain `docker compose up` without exporting `KONG_ENFORCE_ROUTE_POLICY=1` gets the *leaky* edge. Not a doc contradiction but a live-arena footgun for M4 test authors — assert the flag in test setup.
