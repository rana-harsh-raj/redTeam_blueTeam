### 1. How `banking_accounts.account_type = "direct"` rows are created and consumed; every account_type/channel branch

### 3. Routing rules (`direct_account_routing_rules`)

- **PS**: none. No table, config, or symbol. Routing for Direct is expressed solely by sending `preferred_source_account_id` (= `banking_accounts.fts_fund_account_id`) to FTS (§7).
- **FTS** (verified, see §B-D): table `direct_account_routing_rules` (`FTS:internal/migrations/00020_...`: `merchant_id char(14) NULL`, `product`, `channel`, `mode`, `mozart_identifier`, `source_account_id`). Merchant-specific rows have `merchant_id` set; default/global rows have `merchant_id IS NULL` and are matched by `mozart_identifier`. **Rules are consulted only when more than one `source_accounts` row matches `(product, fund_account_id = preferred_source_account_id)`** (`FTS:internal/account/service.go:5333-5349`). With exactly one row (the twin's M2 case: one `source_accounts` row 900002) **no rule is needed**; with several rows and no rule, FTS falls back to `sourceAccounts[0]` with an INFO log — never an error. If **no** source account matches, FTS fails the transfer with `FTS_SOURCE_ACCOUNT_NOT_FOUND` (`transfer_processor.go:662`, `error_code.go:7`) → status FAILED → PS maps to `failed` (Direct listed channels).
- **Monolith**: see Agent A §3.

### 7. FTS request construction for Direct

Built in two layers:
1. `CreateFTARequest` (`PS:internal/app/payouts/processor/fund_transfer_service.go:349-455`): `purpose` (payout.purpose_type or "refund"), `mode`, `narration`, `is_fts` (false only if channel empty → `GetChannelForPayout` line 458-468 returns yesbank/false ⇒ `ErrorTransferRequestFromFundTransferServiceNotAllowed` line 120-135), `status=created`, `version=V3`, `channel = payout.channel`, `initiate_at`, and destination id by CFA instrument (`bank_account_id` w/o `ba_`, `vpa_id` w/o `vpa_`, `card_id`, `wallet_account_id`). Upserts `payout_meta_permanent(meta_name=fund_transfer_service_info, {destination_id,destination_type})` (line 399).
2. `MakeFundTransferServiceRequest` (`PS:pkg/fts/transfer_init_create.go:223-340`) → body `FTSTransferRequestBody{product, merchant_id, account{bank_account|vpa|card|wallet}, merchant_category{onboarded_time,category,mcc}, transfer{preferred_channel, preferred_mode, source_id=payout id, source_type="payout", amount, initiate_at, narration, preferred_source_account_id, is_batch, request_meta{merchant_detail{...},contact_notes...}}}` (struct lines 32-51).
   - `product`: `payout_refund` only when purpose_type=refund AND account not Direct/SubBalance (line 241-246) — Direct refunds go as `payout`.
   - `preferred_channel`: for **non-Direct** `yesbank` is rewritten to `icici` (line 253-256); Direct keeps its channel.
   - `preferred_source_account_id` = `int64(banking_accounts.fts_fund_account_id)` only when `(Direct && channel ∈ {yesbank,axis,icici,rbl,idfc,slice}) || sub_balance` (lines 277-279, 297-299). Parse failure → `ConvertStringToInt64` error at `fund_transfer_service.go:44-56` (`PayoutPreferredSourceAccountIDConversionFailure`, metric `FTSFundAccountIdErrorMetric`). **So `fts_fund_account_id` must be a decimal-integer string (≤14 chars per column) for Direct.**
   - There is **no `source_account_type`, `bank_account_type`, or `source_fund_account_id` field in the PS→FTS create body**. `bank_account_type` and `source_account_id` appear only on the *inbound* FTS status webhook (`dtos.TransferStatusWebhookForPayoutRequest.BankAccountType/SourceAccountId`, used at `fts_transfer_status_webhook.go:512-518,569-575,625-631`) and are persisted to `payout_meta_temporary(meta_name=fts_info,{status,fund_account_id,account_type})` (`core.go:2531-2540`).
   - Gate for the transfer entry-point: `FundTransfer` (`fund_transfer_service.go:25-31`) requires state created/initiated and — for non-Direct — a non-empty `transaction_id`; Direct proceeds without one.
3. Dispatch selection: `FtsAsyncProcessing` (`PS:internal/app/payouts/core.go:5809-5870`): if `IsFTSRequestFromPayoutsService` (config `configs.fts_request_from_ps` whitelist/blacklist, else Splitz `fts_request_from_payouts_service_experiment` variant `fts_request_from_payouts_service`; lines 5931-5969) → PS calls FTS `POST /v1/transfer` directly; else legacy `CreateFTS` (`processor/payoutFTS.go:18-83`) → monolith `GetFTSCreateRequest` (create_fta), in which case the monolith builds the FTS body (Agent A §2).

**900001 / 900002**: `grep -rn '900001\|900002'` across accepted payouts (go/yaml/sql/json/toml, excluding `slits/`) → **0 hits**; 0 hits in pristine/accepted FTS; 0 hits in monolith (Agent A §9).
