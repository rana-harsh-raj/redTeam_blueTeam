## Candidate-by-candidate

### H-D3 — `GET /v1/payouts/free_payout/{balance_id}` cross-tenant read → **VERIFIED_UNAUTHORIZED_EFFECT**

Source: `GetFreePayoutAttributes(ctx, balanceId)` (`freePayout/core.go:678`) calls
`GetBankingAccountByBalanceID(ctx, balanceId)` (`bankingAccount/core.go:391`) and `counters.GetFreePayoutsConsumed(ctx, balanceId, …)`
— all keyed by **balance_id alone, no merchant scoping**. The response DTO (`dtos/freepayoutGetResponse.go`) surfaces
`free_payouts_consumed`, `free_payouts_count`, `free_payouts_supported_modes`.

**Divergent-config canary (decisive design):** the `counters.free_payouts_consumed` row is the observable. Provisioning seeds it to
`0` for every fresh merchant, so I set the **attacker's own** counter to one distinct value and the **victim's** counter to a
**different** distinct value (both non-default; raw integers withheld from the artifact). This is what tells a real IDOR from a
caller-scoped no-op: if A's cross-tenant call returned A's own or the default, no leak; if it returns **B's distinct value**, a real
unauthorized cross-tenant read.

Arms + observations (fresh pair `main`, described — not raw):
- **own_merchant_control** — A reads its own balance → 200, value == A's own canary. (`consumed_is_own_canary=true`)
- **malformed/absent identity** — A's key with a wrong secret and with an empty secret → **401 both** ⇒ A is genuinely
  authenticated as A, not identity-free. (`authenticated_as_A=true`)
- **negative_control_victim_undivergent** — A reads B's balance **while B still held the default counter** → 200 but the value is the
  default; **no distinctive value observable**. This proves causality: any distinctive value seen later comes from B's divergence.
- **merchant_b_variant** — B's counter set to its distinct canary, then A reads B's balance → **200, response carries B's distinct
  value** (≠ A's own, ≠ default); deterministic on repeat.
- **malformed_balance_id** — `free_payout/NOTABALANCE` → **400** (`FreePayoutsInvalidBalanceId`).
- **expected_denial_control** — created a real payout on B, then A fetched it via the **scoped** route `GET /v1/payouts/{id}` →
  **400** "id does not exist". So the scoped route enforces ownership; `free_payout` does not — the asymmetry is specific to this route.
- **state_observation** — B's counter unchanged by A's reads (no mutation); A obtained B's distinctive value.

Deterministic oracle: `unauthorized_effect = A-authed-as-A ∧ no-B-credential ∧ B's-distinct-canary-present ∧ not-A's-own ∧
not-canned-default` → **true**. Negative control (`effect_absent=true`): on the undivergent clean state the effect is absent.
**Independent reproduction:** a **second fresh pair** driven through the attacker **Broker's fixed-identity gateway path** (a distinct
code path from the primary control-plane `kong_call`; deterministic oracle, no model) → **200 with the victim's distinct value →
reproduced=true**. The originating path therefore did not self-certify.

This is a real cross-tenant object-level authorization gap in the **accepted payouts source** (real route, real payouts DB counter,
hardened kong edge). Confirms T06/T14's H-D3 hypothesis with the divergent-config leak they said was needed.

### H-D4 — create quoting another merchant's `fund_account_id` → **NO_UNAUTHORIZED_EFFECT_BENIGN**

Canary: **distinct opening balances** for A and B (x-balances is the authority). `set_mozart_scenario(A, hold)` keeps payouts
`initiated` so binding is observable without a terminal transition.
- **own_merchant_control** — A creates with its own fund account → 200, payout row binds to A (merchant+balance).
- **merchant_b_variant** — A creates quoting **B's `fund_account_id`** → **200 and created**, but the payout row binds to **A**
  (`bound_to_victim_merchant=false`, `bound_to_victim_balance=false`, `bound_to_attacker=true`); deterministic on repeat.
- **expected_denial_control** — A creates with body `merchant_id=B` + A's own fund account → payout still binds to A
  (`body_merchant_id_ignored=true`; passport override, `core.go:415-418`).
- **malformed_fund_account** — garbage id → **400**, not created.
- **state_observation** — **B's balance unchanged**, no payout bound to B.

Oracle: `unauthorized_effect = bound-to-victim ∨ victim-balance-moved` → **false**. Money/state isolation is intact. Note the source
expects a **400** here (`GetCfaFundAccountWithCache(ctx, fa, merchantID)` resolves under the derived merchant); the arena **CFA
substitute** resolves fund accounts without a merchant filter, so the create returns 200 and binds to A. That is a beneficiary-
enumeration / substitute-fidelity nuance, **not** an unauthorized effect — matching T14's H-D4 note.

### F-T10-1 — FTS-direct guard vs monolith-relay route asymmetry → **SOURCE_FAITHFUL_ROUTE_ASYMMETRY**

Precondition = a **link-before-terminal** Direct payout: create via kong under mozart `hold` (→ `initiated`, live FTS transfer), then
set `payouts.transaction_id` to a synthetic BAS id (the state BAS recon would produce). Then deliver a `failed` status on each route:
- **route_fts_direct_with_txn** — POST `http://payouts-api:9400/v1/payouts/transfer_status_webhook`
  (auth `[auth.fts]` = `fts:auth_fts_payouts` — NOT the verifier-bridge/fts identity, which 401s) → **HTTP 500**, payout stays
  **`initiated`**, `transaction_id` retained ⇒ **guard fired** (`VerifyPayoutFailedTransaction`,
  `fts_transfer_status_webhook.go:654-710`, error `ErrorAttemptToMovePayoutToTerminalStateHavingTransaction`).
- **route_monolith_relay_with_txn** — POST `http://monolith-stub:8080/update_fts_fund_transfer` (route E, the arena default) → relay
  200, PS `payout_status_relay` observed, payout **moved to `failed` despite `transaction_id`** ⇒ **guard absent on this route**.
- **negative_control_fts_direct_no_txn** — same FTS-direct route on a fresh payout with **no** `transaction_id` → **HTTP 200**, payout
  **moves to `failed`** ⇒ the guard's refusal is specifically **caused by the `transaction_id` link** (`guard_is_transaction_id_causal=true`).

Source cites: the guard lives ONLY in `HandleTransferStatusWebhookForPayout` (FTS-direct route,
`payout_internal_routes.go:153-158`). Both the Kafka path and the monolith-relay path route through
`HandlePayoutStatusUpdateViaFTS` (`core.go:1465-1585`) which has **no `VerifyPayoutFailedTransaction`** (T02 §8(b)(c), T05 route
table D vs E, matrix rows 18/19). So the relay path's behaviour is **faithful to the accepted PS source**, not a substitute defect.

Why not a finding: (1) `unauthorized_effect=false` — this is a terminal-state-integrity question, not a cross-tenant/money effect;
(2) the relay endpoint that lacks the guard is the **monolith-stub substitute**, and whether the **production** monolith
(`api Payout/Core.php` FTA update) carries its own upstream statement-first guard is **out of the accepted-payouts corpus**
(T10 §7). Asserting a terminal-state-integrity invariant violation would require that out-of-corpus confirmation. The live replay
therefore records the asymmetry and classifies it source-faithful; T10's run `m4-bas-ingest-20260906T194947Z` step (f) independently
recorded the same asymmetry through the full BAS-link pipeline.

## How the driver avoids self-certification / preserves honest negatives

- The verdict is a **deterministic oracle** over booleans, never a model, and never the originating worker's own say-so.
- H-D3's independent reproduction runs on a **second fresh pair** through a **different mechanism** (attacker Broker gateway path).
- Every candidate has a **negative control** proving causality: H-D3 (undivergent victim → no leak), H-D4 (own-control binds to A +
  B untouched), F-T10-1 (no-txn payout moves to failed → the guard is txn-caused).
- Fresh merchant/resource ids every run; no raw canary or credential values in the artifact (descriptors use `public_view`, secrets
  stay in the Broker's memory). The two benign results (H-D4, F-T10-1) are reported **as** benign with the divergent-config / route
  evidence, not upgraded.

- H-D4: **real** payouts create + real x-balances authority; **CFA is an arena substitute** (the 200-instead-of-400 is a substitute
  fidelity gap, money-safe).
- F-T10-1: **real** payouts routes (FTS-direct + PS relay handler) + real payouts DB; the **monolith relay is the monolith-stub
