Invariants that must hold across the closure (candidate test oracles):
1. Every `created` payout has exactly one `payout_initiated` journal; every `processed` (Shared) eventually one `payout_processed`; every `reversed`/`failed` exactly one mirror journal; MerchantBalance debits/credits sum to zero across the payout lifecycle.
2. No payout reaches `processed` without an FTS transfer in `PROCESSED` with a UTR; no payout stays `initiated` while its transfer is terminal (this invariant is currently violated in production and has no automated repair).
3. `(idempotency_key, merchant_id)` returns the same payout id; `(source_id, source_type)` returns the same transfer id.
4. A payout is never visible to a different merchant through public routes (internal routes do not guarantee this).
5. In-flight reservation total equals the sum of amounts of live reservations for non-terminal dispatched payouts (reconciler rebuilds every 5 min).
6. Merchant webhooks for a payout contain every terminal state exactly once (ordering not guaranteed).
