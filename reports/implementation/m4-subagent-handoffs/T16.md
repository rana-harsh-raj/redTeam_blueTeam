## The panic (observed 2026-09-06T19:41:42Z, merchant ARENAD80422548)

```
panic: type mismatch: cannot convert int64 to bool
protoreflect Value.Bool -> payouts pkg/dcs/features/features.go:252 EnabledFeaturesForKeyFromResponse.func1
-> goutils/dcs server.go:122 EnabledFeatures -> payouts pkg/dcs/service.go:26 GetEnabledFeatures
-> merchant/core.go:524 fetchFeaturesFromDcsSimple -> fetchAllFeaturesConcurrently.func2
```

## Exact offending object / field / value

- **object_name:** `rzp/x/merchant/payouts/FundTransfer`
- **field_name:** `queue_payout_bal_buffer` (proto **field 6, type int64**)
- **wire value:** `50000` (varint `d08603`) for ARENAD80422548 (and ARENAD83156710); fixture ARENAM00000002=50000, ARENAM00000003=100000, ARENAM00000001=0.
  Seed: `ENV2_COMPOSE/seeds/{dcs,generated/dcs}/merchants.json`.
- **stub schema line:** `ENV2_COMPOSE/substitutes/dcs-stub/server.py` `FIELD_SCHEMAS["rzp/x/merchant/payouts/FundTransfer"]` `(6, "queue_payout_bal_buffer", "int64")` — the only non-bool field in a FundTransfer object that otherwise holds bool feature flags.

## Why it panicked (call-site citations)

1. `GET /v1/payouts/_meta/summary` -> `internal/app/merchant/core.go:524 fetchFeaturesFromDcsSimple` builds `merchantFeatures := dcsFeatures.MerchantFeatures()` (only **bool** flags; the int64 `queue_payout_bal_buffer` is **not** in that list — `pkg/dcs/features/features.go:261+ MerchantFeatures()`).
2. `pkg/dcs/service.go:19 GetEnabledFeatures` -> goutils `EnabledFeatures` (`goutils/dcs@v1.7.3/server/service.go:76`) groups the requested flags **by DCS object key** and issues one `Get` per object with `Fieldmasks` = exactly the requested field names (bool-only for FundTransfer).
3. goutils hands each response object to `pkg/dcs/features/features.go:241 EnabledFeaturesForKeyFromResponse`, which unmarshals the object and `m.ProtoReflect().Range(func(...) { if v.Bool() {...} })` — calls `.Bool()` on **every populated field** (features.go:251-256).
4. The dcs-stub **ignored the fieldmask** and returned the whole FundTransfer object including the populated int64 `queue_payout_bal_buffer` (field 6). `.Bool()` on the int64 -> `protoreflect` panic -> process exit.

Reproduced (OR-path, no route crash needed) against the live stub with ARENAD80422548 + the bool-only fieldmask from the crash path: response contained `(6, 50000)` — the int64 leak — proving the trigger.

## Classification: **substitute bug** (case a), NOT source fragility

Production DCS applies the query's per-slot fieldmask as a **redaction after the read** — the returned object carries only the listed fields; an empty fieldmask returns the whole object. Ground truth in the pinned DCS clone:
- `dcs/internal/kv/helper.go` `redaction.apply()` (`len(fields)==0 || redactFn==nil -> value unchanged`, else `redactFn(value, fields)`).
- `dcs/internal/kv/service.go:436 redactionForQuery` builds that per-slot redaction from `query.Fieldmasks`.
- test `dcs/internal/kv/helper_test.go:219 TestEvaluateFeatureValue_FieldmaskExcludesUnlistedFields` asserts unlisted fields are dropped.

So production, on this exact EnabledFeatures path, never returns `queue_payout_bal_buffer` (it is not in the bool-only fieldmask) and payouts' `Range/.Bool()` never sees a non-bool field. The panic is an artifact of the stub over-returning, not of a real production object that legitimately carries an int64 on this path. Hence the fix belongs in the stub (declared substitute fix), and no payouts source patch and no provisioner change are warranted. (For the record: had it been genuine source fragility, a crash from a merchant's *own* config would be a reliability observation, not a cross-tenant/security finding — but that is not this case.)

## The fix (diff summary)

File: `ENV2_COMPOSE/substitutes/dcs-stub/server.py`
- `_resolve_value_bytes(entity_id, key)` -> `_resolve_value_bytes(entity_id, key, fieldmask_names=None)`: when `fieldmask_names` is non-empty, filter stored `values` to only those field names before `encode_message`. Empty/absent -> whole object (production `redaction.apply` semantics).
- New helper `_fieldmask_names(q)`: pulls `[{"name": ...}]` from a query's `fieldmasks`.
- `_get_or_evaluate` passes `_fieldmask_names(q)` into `_resolve_value_bytes`.
- Docstrings updated; stdlib-only proto encoder/decoder untouched; no other key/route changed. `_put`/`_patch` fieldmask handling unchanged.
