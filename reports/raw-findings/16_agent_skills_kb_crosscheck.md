## 5. Contradictions — detailed verdicts

### 5.1 Ledger: "part of API Monolith" vs. standalone service (strong contradiction)

- **KB claim** (`modules/services/ledger.md:5`): *"Language: Part of API Monolith (PHP) for VA payouts; being moved to standalone Ledger service."* This directly conflicts with the KB's **own** `SKILL.md`/`core/architecture.md` diagrams, which already draw Ledger as a separate box called by Payout Service via gRPC/HTTP — i.e. the KB contradicts itself internally, and the service-detail page is the stale half.
- **Code evidence** (findings 04, `razorpay/ledger` @ `471ff4d5`): Ledger is a fully independent, multi-tenant (TenantX for RazorpayX, TenantPG for the legacy PG monolith) double-entry accounting service — Go, Twirp RPC, Postgres, its own CODEOWNERS (`@razorpay/ledger-team`), its own Spinnaker deploy, called synchronously over HTTP/Twirp by Payouts/FTS/x-balances via Basic Auth (`auth.payouts`, `auth.fts`, `auth.xbalances`). This is **already** the "standalone service" the KB says is a future migration target.
- **Independent corroboration** (findings 02 items 1-6; findings 11§C): Payout Service's own code calls `github.com/razorpay/ledger-sdk` against host `ledger-live.dev.razorpay.in`/`ledger-live.razorpay.com`, with Hystrix circuit breaker — this is unambiguous, confirmed-confidence, cross-repo evidence.
- **Verdict**: **Contradiction resolved in favor of the code.** Ledger is not PHP-monolith-embedded; it is a standalone service today, not a future state. The KB's `ledger.md` file is either stale (written before an earlier extraction) or was never verified against the real Ledger repo (unlike, e.g., `modules/services/cfa.md`, which correctly identifies CFA's MongoDB store with specifics that match findings 05).

### 5.2 FTS status delivery: "Kafka is the newer, preferred, equivalent path" vs. Kafka explicitly ignoring terminal-failure states (strong contradiction)

- **KB claim** (`modules/services/payout-service.md:126`, `modules/services/fts.md:157`, `SKILL.md` issue #4, `guides/on-call-debugging.md` Scenario 1 Step 4): FTS delivers status via HTTP webhook **OR** Kafka topic `fts_status_updates`, "both handlers call the same underlying logic," Kafka is described as "the newer, preferred route." The on-call guide instructs engineers to check both paths as roughly interchangeable.
- **Code evidence** (findings 02, item 12 — confirmed confidence): `internal/taskHandlers/fts_status_updates.go:56-60` — *`if inputStatus == StateReversed || inputStatus == StateFailed { return nil }`* — the Kafka consumer **explicitly no-ops** on `reversed`/`failed` status updates. Code comment: *"api code has very tight coupling between api, payouts service and ledger for handling reversed updates"* — i.e. for the two terminal states that matter most for money-loss risk, **API Monolith remains the source of truth**, not Payout Service via Kafka.
- **Independent corroboration** (findings 11§D): Slack evidence, reconstructed via full code trace in a live debugging thread, confirms the terminal-status callback from FTS to Payouts is a **synchronous HTTP webhook**, not Kafka-based, and that Kafka/CDC in this area is used for a *different* pipeline (IRCTC/Catalyst ledger posting), not the general terminal-status path.
- **Verdict**: **Contradiction resolved in favor of the code + Slack evidence (two independent sources).** The "both paths are equivalent, Kafka preferred" framing is materially wrong for exactly the two states (`failed`, `reversed`) where getting the debugging playbook wrong has the highest money-loss consequence. This is the single most operationally dangerous inaccuracy found — an on-call engineer following `guides/on-call-debugging.md` Scenario 1 Step 4 as written could waste time chasing a Kafka consumer-lag red herring for a reversed/failed payout when that path is a documented no-op for those statuses.

### 5.3 Webhook delivery: "API Monolith → Stork" vs. Payout Service → Stork directly (partial contradiction)

- **KB claim**: `core/architecture.md:99` and `modules/services/api-monolith.md` draw the notification path as `API Monolith → Stork → Merchant`, with Payout Service only "requesting" notification from API Monolith.
- **Code evidence** (findings 02, items 24-25): Payout Service calls Stork **directly** via a generated Twirp `WebhookAPI` client (`pkg/stork/client.go`), for merchant webhooks specifically — with optional payload encryption before send.
- **Independent corroboration** (findings 11§E): "`payout.*` webhooks... sent from the Payouts Service to Stork" — directly attributed in a live incident thread.
- **Verdict**: KB is correct for the *legacy SMS/email* path (which genuinely does run through API Monolith's `PayoutProcessedContactCommunication`) but wrong to draw this as the single/primary notification arrow for merchant **webhooks**, which bypass the monolith entirely.

9. **Ledger's real double-entry accounting model** (§4 #5) — lower urgency than #1-3 since the simplified "debit/credit back" mental model is directionally not wrong, but anyone reconciling ledger entries against the KB's description will be confused by VendorPayable/FtsPayable/FtsReceivable account movements the KB never mentions.
10. **Ownership/escalation table gaps** (§4 #16) — mis-routing Ledger escalations to "Payouts on-call" instead of the separate Fin-Infra/Ledger team is a process-correctness gap, lower engineering-risk than #1-7 but real for incident response speed.
