## 1. Current-state description

### 1.1 How a "hypothesis" is represented today

Source: `/Users/rana.singh/rzp-payouts-architecture/RED_LOOP/red_loop/state.py:88-100`
and the tool schema `/Users/rana.singh/rzp-payouts-architecture/RED_LOOP/red_loop/tools.py:64-77`.

- Stored append-only in `RED_LOOP/runs/<cid>/hypotheses.jsonl`. Each base record:
  `hypothesis_id` (`"H-%03d"`, sequential), `claim`, `assets[]`,
  `preconditions{}` (always `{}` in practice — the tool never sets it),
  `suspected_weakness`, `expected_impact`, `planned_experiment`, `status`,
  `evidence_refs[]` (never populated).
- Updates are appended as separate records with `_update: true` and folded by
  `latest_hypotheses()` (`state.py:184-192`) — last-writer-wins per field.
- **Status is a free-text string.** `update_hypothesis` (tools.py:74-77) documents
  only `proposed|testing|supported|refuted`; `campaign.py:_progress_signature`
  (line 45-51) counts `supported|confirmed|refuted`; `context.compile_state_message`
  (context.py:41-48) buckets `proposed|testing` → active, `supported|confirmed` →
  supported, `refuted|failed|rejected` → refuted. There is **no enum, no validation,
  no state machine**. Nothing enforces legal transitions.
- There is **no**: unique semantic fingerprint, target-asset typing, labeled
  precondition provenance (verified/observed/assumed), success/stop condition,
  max-actions/max-duration budget, owner, terminal-status reason, next-best-action,
  or priority field on a hypothesis. `expected_impact` and `planned_experiment`
  are the closest existing analogues to "expected observation" and "bounded
  experiment" but are unstructured prose.
- Real runs barely use it: `camp-20260906T154844Z-23100f` recorded exactly **1
  hypothesis, 0 observations, 0 candidates** before stagnation stop. The lifecycle
  is effectively unused today.

### 1.2 How the campaign loop works

Source: `/Users/rana.singh/rzp-payouts-architecture/RED_LOOP/red_loop/campaign.py`
(entry `run_campaign`, line 93).

Turn structure (while-loop, line 134):
1. Check STOP/PAUSE files, emergency turn ceiling, wall clock, request budget
   (lines 135-150). STOP/PAUSE are files under the run dir.
2. Compile a **bounded** state packet from the durable store, not the whole
   transcript (`context.compile_state_message`, `context.build_messages`), plus a
   rolling raw window of the last `DEFAULT_RAW_WINDOW=6` assistant turns
   (context.py:22, trim_raw_window line 119).
3. `_complete_with_model` (line 54): one completion; on blank/content-filter/refusal
   (`llm.is_unusable`, llm.py:155) retry once with a smaller packet, else switch to
   a distinct model from the live gateway inventory (`llm.pick_fallback`).
4. Dispatch every returned tool call via `tools.Dispatcher.dispatch` (line 215-229);
   append tool results to the raw window (truncated at 40 KB).
5. If `conclude` was called, stop with `CONCLUDED`.
6. Progress/stagnation accounting (lines 236-284):
   - `_progress_signature` = (hyp count, obs count, cand count, #verified obs,
     #resolved hyps, #unique recent fingerprints). Unchanged signature → increment
     `turns_since_progress`.
   - **recon-only loop**: `recon_only_streak` counts turns with no runtime
     experiment (`merchant_request*` / `read_own_webhooks`). At `recon_patience`
     (≥8) it fires a one-shot **replan nudge**; a second time it STOPs as
     `stagnation_pause`.
   - **fingerprint stagnation**: `turns_since_progress >= stagnation_patience(14)`
     with ≥12 recent fps and ≤3 unique → one-shot replan nudge, then STOP.
7. Every 5 turns, checkpoint to `manifest.json` via `update_manifest` (turns,
   usage, broker counts, `state_hash`).

Stop reasons (`StopReason`, line 20-32): `agent_concluded`, `kill_switch`,
`emergency_turn_ceiling` (backstop, **not** normal), `max_wall_ceiling`,
`request_budget_exhausted`, `stagnation_pause`, `all_hypotheses_resolved` (defined
but **never assigned**), `model_unrecoverable`. `NORMAL_COMPLETIONS` excludes the
emergency ceiling. The loop is a **single explorer, single context** — there is no
notion of parallel workers, leases, or multiple exploration policies.

Resume: `run.py:resume_campaign_cmd` (line 225) rebuilds store/broker/judge from
the manifest, re-derives active hypotheses from the store (the model conversation
is intentionally discarded), and calls `run_campaign(..., resume=True)`. Restart
recovery is real and tested by `surface/m3_recovery_test.py` (kill -9 the runner,
resume from durable JSONL, assert turns advance and side-effecting actions are not
blindly repeated).

### 1.3 Candidates / judge / reproducer

- **Candidate**: `claim_candidate` tool (tools.py:85-96) → `store.add_candidate`
  (`"C-%03d"`) with `claimed_outcome`, `minimal_steps[]`, `affected_assets[]`,
  `suspected_root_cause`, `evidence_summary`, `capabilities[]`, `status:"claimed"`.
  Dispatch immediately calls the **judge hook** (run.py:167) for inline coarse
  pre-adjudication; the agent gets back only
  `{recorded, deterministic_impact_confirmed}` (COARSE — never the verdict class).
- **Judge** (`red_loop/judge.py`): authoritative, deterministic. `Evidence` reads
  payouts/FTS MySQL and Ledger Postgres and the webhook sink via `docker exec`
  (judge.py:53-177). `admit()` (line 295) is a minimum-evidence gate classifying
  impact into confidentiality/integrity/availability and requiring a real
  canary/cross-owned resource / attacker-attributed transition / invariant
  violation — a bare 200 never passes. `adjudicate()` (line 402) returns one of 10
  `VERDICTS` (line 29). `scan_invariants` checks ledger zero-sum and idempotency
  dedup; `scan_canaries` matches hidden victim strings. `KnownGaps.classify`
  downgrades demonstrated effects that match `registry/known_gaps.yaml`
  (Kafka expected failures → CALIBRATION_REDISCOVERY, substitutes → TWIN_SPECIFIC_LEAD,
  fidelity ceilings → NEEDS_HIGHER_FIDELITY, declared deviations → DECLARED_DEVIATION).
- **Reproducer** (`red_loop/reproducer.py`): only fires post-campaign for verdict
  `ACCEPTED_NEW_FINDING` (run.py:201-207). A different provider (default `gpt-5.5`)
  gets a **minimal bundle** (actor, steps, required inputs, claimed result, allowed
  code slices) — never the primary's narrative, the judge classification, or the
  known-gap registry. Uses fresh idempotency keys and the same brokered boundary.
  If there are no positives, `run.py:_run_calibration` runs a private own-tenant
  self-test of the reproduce+judge machinery (NOT a finding).

### 1.4 Model call path (LiteLLM via llm.py)

- `red_loop/llm.py:ChatClient.complete` (line 86) POSTs OpenAI-schema
  `/v1/chat/completions` to the gateway with `Authorization: Bearer <key>`.
  Stdlib `urllib` only. Retries 4× with backoff; 400/401/403/404/422 are
  non-retryable. `redact()` scrubs the key from any persisted string.
- **Env var NAMES only** (from `RED_LOOP/llm.env`, values never read):
  `LITELLM_BASE_URL`, `LITELLM_API_KEY`. Read via `config.gateway_base()` /
  `config.gateway_key()` (config.py:24-34). Optional model overrides (config.py:42-45):
  `REDLOOP_PRIMARY_MODEL`, `REDLOOP_REPRODUCER_MODEL`, `REDLOOP_UTILITY_MODEL`, and
  `KONG_LITE_HOST_URL`.
- **Model selection registry**: `run.py:write_models_artifact` (the `models`
  subcommand) pulls `/v1/models`, records the live inventory, and writes the
  selected primary/reproducer/utility + rationale + unavailable list to
  `registry/model-selection.json`. Selection itself is **static** in `config.py`
  (env-overridable); the registry file is documentation/audit, not a live router.
  Fallback at runtime is dynamic via `llm.pick_fallback` over the live inventory.
  Note the M3.1 campaign actually ran on **kimi-k3** as primary (see manifest of
  `camp-20260906T154844Z-23100f`), so the effective primary was overridden via the
  `REDLOOP_PRIMARY_MODEL` env var for that campaign — config default remains
  `claude-opus-4-8`.

### 1.5 Evidence hashing / indexing

- `state.CampaignStore.put_evidence` (state.py:148-160): content-addressed —
  `sha256` of the blob, filename `"<label>-<digest[:16]>.<ext>"` under
  `runs/<cid>/evidence/`. `state_hash()` (line 166) hashes the concatenation of
  the decision ledgers (hypotheses, actions, observations, candidates, responses,
  events) — excludes volatile model_calls/context_metrics — for before/after
  restart proofs.
- `run.py:evidence_index` walks the whole run dir and writes
  `evidence-index.json` = list of `{path, sha256, bytes}`. `archive/build_manifest.py`

### 1.6 How M3.1 acceptance consumed campaign records

`surface/m3_1_acceptance.py:build()` derives every gate from named artifacts (no
hand-set booleans). The campaign-facing gate is **H. `second_open_campaign`**
(line 213-238): loads `runs/<cid>/manifest.json`, requires
`completion.stop_reason ∈ {agent_concluded, stagnation_pause, all_hypotheses_resolved}`,
`normal_completion == true`, `ended_on_emergency_ceiling == false`,
`attacker_is_fresh_funded == true`, clean same-window egress, and a recorded
`primary_model`. **Crucially it does NOT inspect hypotheses.jsonl at all** — a
campaign that closes "successfully" with a single `proposed` hypothesis and zero
observations passes the gate. That is exactly the M4 hole this task must close.

## 3. Migration design (concrete, minimal, backward compatible)

**Guiding rule (from the mandate): do not replace the working runtime.** The
existing `campaign.py`/`state.py`/`judge.py`/`reproducer.py` loop stays intact and
runnable exactly as today. M4 features are added as **new modules the loop and
tools opt into**, plus an **adapter** that projects the legacy `hypotheses.jsonl`
records onto the new lifecycle so old runs remain readable.

### 3.1 New modules

1. **`red_loop/hypotheses.py`** — the lifecycle state machine + fingerprinting.
   - `class HypothesisState(str, Enum)` with exactly the M4 states:
     `PROPOSED, CLAIMED, EXPERIMENT_DEFINED, EXECUTING, EVIDENCE_GATHERED,
     FALSIFIED, BLOCKED, SUPPORTED, REPLAY_REQUESTED, REPRODUCED, REJECTED,
     ACCEPTED, CLOSED`.
   - `LEGAL_TRANSITIONS: dict[state, set[state]]` and
     `advance(record, to, reason, actor)` that raises on an illegal edge and
     stamps `terminal_status_reason` when entering a terminal state
     (FALSIFIED/BLOCKED/ACCEPTED/CLOSED/REJECTED).
   - `class Blocker(str, Enum)` — the **fixed enum**: `ROUTE_NOT_EXPOSED,
     REQUIRED_ACTOR_UNAVAILABLE, SERVICE_NOT_MODELED, FIDELITY_INSUFFICIENT,
     MISSING_EVENT_CONSUMER, MISSING_TOOL_CAPABILITY, ENVIRONMENT_FAILURE,
     TIME_BUDGET_EXHAUSTED`. `BLOCKED` requires a `blocker` value; a validator
     forbids `BLOCKED` being treated as `FALSIFIED` in any rollup.
   - `fingerprint(target_assets, claim, suspected_cause) -> str`: normalize
     (lowercase, sort assets, strip ids/uuids/`pout_*`, collapse whitespace),
     `sha256`, take 16 hex. Reuses the id-stripping idea already in
     `judge._extract_payout_ids`.
   - `class Priority(IntEnum): CRITICAL=0, HIGH=1, MEDIUM=2, LOW=3`. "Highest
     priority" = min(priority) among non-terminal hypotheses, ties broken by
     earliest `created_at` (stable). `highest_priority_open(hyps)` helper.
   - `duplicate_of(new_fp, existing) -> hid|None` for semantic dedup.

2. **`red_loop/leases.py`** — cooperative task leases over the durable store.
   - `Lease{lease_id, hypothesis_id, owner, acquired_at, expires_at, heartbeat_at}`
     persisted to a new `leases.jsonl`. `acquire(hid, owner, ttl)`,
     `heartbeat(lease_id)`, `release(lease_id)`, `reap_expired(now)` →
     expired leases free their hypothesis for reassignment and emit a
     `lease_expired` event. Uses the same fsync append discipline as `state.py`.

3. **`red_loop/contexts.py`** — multi-context orchestration (≥4 policies).
   - `class ContextPolicy{name, mandate_suffix, tool_allowlist, target_bias}` and a
     `POLICIES` list of the four required policies (see 3.6). Each policy is a
     thin wrapper that runs the **existing** `run_campaign` with (a) a policy-
     specific mandate suffix appended to `prompts/primary_mandate.txt` and (b) a
     `tool_allowlist` filter injected into `Dispatcher` (new optional
     `allowed_tools` arg — default None = all, preserving current behavior).
   - `orchestrate(store, policies, ...)` runs them as isolated contexts (separate
     raw windows, separate lease owners, one shared durable store + one shared
     judge). Sequential by default; parallel is an opt-in future step.

4. **`red_loop/soak.py`** — long-run coordinator.
   - Loop over N cycles: rotate scenario/policy, checkpoint each cycle, suppress
     duplicate hypotheses via `hypotheses.duplicate_of`, reap+reassign expired
     leases, and at the end emit a **machine-readable** `soak-summary.json`
     (per-policy turns, hypotheses by terminal state, blockers by enum, accepted
     findings, dup-suppressed count).

5. **`red_loop/experiments.py`** (small) — the cross-merchant experiment template.
   - `class CrossMerchantExperiment` requiring the seven arms: `own_control`,
     `merchant_b_variant`, `malformed_identity_variant`, `absent_identity_variant`,
     `expected_denial_control`, `state_observation`, `clean_reset`, and a
     `requires_independent_replay=True` flag on any unauthorized effect. A
     validator refuses to mark such a hypothesis `SUPPORTED` unless every arm has
     a recorded observation and the replay was independent.

### 3.3 Hook points (minimal edits, all additive/opt-in)

- `tools.py`: add lifecycle tools `define_experiment`, `mark_blocked(blocker, note)`,
  `request_replay`, and extend `record_hypothesis` to accept the v2 fields
  (keeping the old signature working — new fields optional). `Dispatcher.__init__`
  gains optional `hyp_manager`, `lease_manager`, `allowed_tools`.
- `state.py`: add `add_hypothesis_v2`, `advance_hypothesis`, `latest_hypotheses_v2`
  reading `hypotheses_v2.jsonl`; **do not touch** the existing methods. Add an
  `adapter.project_legacy(hyp)` that maps old `status` → v2 state
  (`proposed→PROPOSED`, `testing→EXECUTING`, `supported/confirmed→SUPPORTED`,
  `refuted/failed/rejected→FALSIFIED`) so mixed/old runs render.
- `campaign.py`: `_progress_signature` also counts v2 terminal states; the
  stagnation replan writes a **recorded reasoned replan** (a `replan` record with
  the next-best action) instead of only a transient nudge. No change to the stop
  machinery.
- `judge.py`: unchanged internals; a positive verdict now drives
  `advance_hypothesis(hid, REPLAY_REQUESTED)` and, on reproduction,
  `REPRODUCED`/`REJECTED` then `ACCEPTED`/`CLOSED`. Blocked/denied paths advance to
  `BLOCKED` with a blocker, never `FALSIFIED`.
- `reproducer.py`: unchanged; its result maps to `REPRODUCED`/`REJECTED`.

### 3.4 The closing gate

Add gate **`lifecycle_discipline`** to `surface/m3_1_acceptance.py` (and its M4
successor). It loads `hypotheses_v2.jsonl`, computes `highest_priority_open`, and
**fails closed** if the highest-priority hypothesis is still `PROPOSED` or
`CLAIMED` while the campaign claims success. Also fails if any hypothesis is
`BLOCKED` without a valid `blocker` enum value, or `SUPPORTED` on an unauthorized
effect without a recorded independent replay. This is the direct fix for the §1.6
hole. Implement as a new function `lifecycle_gate(campaign_id)` returning the same
`gate(...)` shape already used at `m3_1_acceptance.py:53`.

### 3.6 The four context policies (prompt/mandate + tool-allowlist variants)

All four share the base `prompts/primary_mandate.txt` (unchanged) plus a
policy-specific suffix and an allowlist over the existing tools in `tools.py`.

1. **`broad-coverage`** — suffix: "survey the full merchant surface; breadth over
   depth; open many shallow hypotheses." Allowlist: all read/probe tools
   (`merchant_request`, `code_*`, `record_*`, `recall`). No concurrency.
2. **`deep-direct-accounting`** — suffix: "focus on the Direct payout path and
   ledger zero-sum / reversal / idempotency invariants; go deep on one asset."
   Allowlist: `merchant_request`, `read_own_webhooks`, `code_*`, `record_*`,
   `claim_candidate`.
3. **`identity-tenant-boundary`** — suffix: "probe identity resolution and
   cross-tenant authorization; every experiment must include own-control +
   merchant-B variant + malformed/absent identity + expected-denial control."
   Allowlist adds `merchant_request` with `X-Razorpay-Account` variation; binds
   the `experiments.CrossMerchantExperiment` template.
4. **`concurrency-event-order`** — suffix: "probe races, duplicate delivery, and
   event ordering (idempotency, dedupe, webhook duplication)." Allowlist includes
   `merchant_request_concurrent` (the only policy that gets it) + `read_own_webhooks`.

### 3.7 Failure-recovery test harness

New `surface/m4_recovery_matrix.py` generalizing the existing
`surface/m3_recovery_test.py` (which already does explorer kill+resume). Each
scenario asserts durable state (compare `store.state_hash()` before/after,
confirm active hypotheses/leases survive, confirm no side-effecting action is
blindly repeated):

- **explorer kill** — `kill -9` the runner (as m3_recovery_test does), resume.
- **subagent kill** — kill a context worker mid-lease; assert `reap_expired`
  reassigns its hypothesis.
- **model-provider timeout** — point `LITELLM_BASE_URL` at a **fake local gateway**
  (a stdlib `http.server` returning 504/hangs) via env; assert
  `_complete_with_model` recovers or switches and the turn is not counted as
  progress. No real model call.
- **service restart** — `docker restart` a twin container between turns; assert the
  loop tolerates transient judge/evidence errors (`INSUFFICIENT_EVIDENCE` fallback
  at run.py:176) and continues. (Requires docker — flag as environment-gated.)
- **queue consumer restart** — restart the webhook sink / Kafka consumer; assert
  webhook reads degrade gracefully.
- **DB restart** — restart mysql-payouts/postgres-ledger; assert judge retries and
  the campaign state is intact.
- **partially written artifact** — truncate the last line of a `*.jsonl` mid-record;
  assert `_read_all` skips the bad line (it already `try/except`es JSON at
  `state.py:81-84`) and the run resumes.
- **expired lease** — advance the clock past TTL; assert reassignment + handoff record.
- **interrupted replay** — kill the reproducer mid-bundle; assert the hypothesis
  stays `REPLAY_REQUESTED` (not falsely ACCEPTED) and can be retried.
- **interrupted acceptance** — kill between REPRODUCED and ACCEPTED; assert the
  closing gate treats it as not-yet-accepted.

The fake-gateway simulator is the key reusable piece: a tiny local HTTP server
(started in-process) whose URL is injected via the existing `LITELLM_BASE_URL`
env var — no change to `llm.py` needed, satisfying "no real model calls" for the
timeout scenario.

## 5. Risks, unresolved questions, confidence, handoff

### Top risks
1. **The twin has no genuine cross-tenant vulnerability** (M3.1 completion + fidelity
   docs). The full M4 lifecycle can be *exercised* but will keep terminating in
   `BLOCKED (fidelity_insufficient)` / `SUPPORTED`-only-on-controls, not `ACCEPTED`.
   The lifecycle machinery must be validated on the **fresh-ID calibration fixture**
   (`calibration/tenant-isolation/`), which has a real IDOR regression, not on the
   live campaign — otherwise the failure-recovery and cross-merchant tests have no
   positive path to exercise.
2. **Judge/evidence and several recovery tests hard-depend on `docker exec`** into
   named `env2_compose-*` containers (judge.py:22-27, provisioner, m3_recovery).
   T08 is read-only/no-docker so none of this was executed; the service/DB/queue
   restart scenarios are environment-gated and unverified here.
3. **Effective primary model is unpinned**: config default (`claude-opus-4-8`)
   diverges from what M3.1 actually ran (`kimi-k3` via env). The M4 multi-context
   design multiplies model calls 4×; with `claude-opus-5` budget-capped and
   content-filtered, provider budget exhaustion is a live risk. Pin per-context
   models explicitly and keep `llm.pick_fallback` as the safety net.

### Unresolved questions
- Should the four contexts run **in parallel processes** (true leases/reassignment)
  or **sequentially** (simpler, still satisfies "isolated contexts")? Recommend
  sequential first (backward compatible, one shared store), parallel as a later step.
- Priority assignment: agent-declared vs harness-derived from impact class? Recommend
  harness-derived from `capabilities` (integrity>confidentiality>availability) to
  avoid the agent gaming its own gate.
- Does M4 want the legacy `hypotheses.jsonl` migrated in place or dual-written?
  Recommend **dual-write + adapter** (kept the old file untouched) for safety.

### Confidence
High on current-state facts and the gap matrix (read every module and real run
records). Medium on the migration effort estimate — the state-machine + gate +
tests are small and self-contained; the multi-context orchestration and the
docker-gated recovery scenarios are the larger, riskier pieces.
