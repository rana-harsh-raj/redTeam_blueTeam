## (a) What changed after gaining access

### API monolith (`razorpay/api`, finding 20)
Full payout route table now available (`app/Http/Route.php`, 23,164 lines) — every `payout_*`/`payouts_service/*`/`fund_account_validate*` route name, HTTP method, URI, auth-group membership (`$public/$private/$proxy/$admin/$internal/$device`), and controller action is enumerated with line numbers (20 §1). Two independent, coexisting proxy-to-Payouts-Service mechanisms exist on `POST /v1/payouts`: a Splitz-gated "direct" bypass (`DirectToPayoutsServiceGate::shouldDivert()`, header `X-Payouts-Service-Proxy: 0`, no monolith-side business logic runs) and the older classic path that runs full validation/balance/pricing logic before proxying (`X-Payouts-Service-Proxy: 1`) (20 §2). Dashboard authentication mechanics are now visible: IP allowlist via `MerchantIpFilter`, OTP mandatory for `payouts_with_otp` and for non-partner approvals, ICICI-specific 2FA as a separate pending-then-approve flow — but **`merchant_users` membership is not checked inside `api` at all**; the monolith trusts the Passport JWT minted upstream by Edge (20 §3). Admin-dashboard/ops permission enforcement is confirmed **local and DB-backed** (`AdminAccess::policyChecker`, admin→role→permission in the monolith's own schema) — the only "AuthZ" client found (`Services/Mock/AuthzEnforcerClient`) lives under a `Mock` namespace, not production (20 §7). The FTS-webhook relay (`/v1/update_fts_fund_transfer` → `FundTransferAttemptController@updateSource`) has **no retry** on the downstream PS call — single attempt, re-throws on failure — and commits the FTA row to the local DB *before* attempting the PS relay (20 §4). The `/payouts_service/dual_write` mechanism is queue-backed (5 retries) and, read end-to-end, moves data **PS → monolith's own local `payouts` table** (upserting a shadow copy), writing only a small bookkeeping watermark into PS's own database — this supersedes a conflicting earlier draft that had the direction backwards (20 §8). `bas_recon_payout_update` is allowlisted only under the `payouts_service` service credential — **PS, not XAS, is the caller**, and a reversal is created only for a local (non-PS) payout currently `FAILED` (20 §9). No FAV-freshness gate exists anywhere in the Payout module (exhaustive grep) (20 §6).

### Edge / Kong (`terraform-kong`, `edge`, finding 21)
`payouts-proxy-cutover` is instantiated in exactly one place, `base/payouts-proxy-cutover/` — **devstack only**; no prod/stage/us/sg environment diverts any payout route to Payouts Service. Every prod payout/contacts/fund_accounts route stays on the monolith today (21 §1). Passport minting is Kong's `upstream-jwt` plugin (`edge/kong-plugins/kong-plugin-upstream-jwt`), RS256, hardcoded 300s TTL, and the full claim schema is now enumerated field-by-field (21 §2). **No `authType` claim exists in the JWT** — `auth_type`/`auth_flow` is Kong-internal request context only. **No rate-limiting plugin is wired to any payouts/contacts/fund_accounts route** anywhere in either repo. **No loop-guard mechanism** (`X-PS-Proxied` or equivalent) exists for the direct-divert design — confirmed absent, not merely unfound. `authz-enforcer` runs `shadow_mode=true` **and** the public-API route is explicitly whitelisted, so it never blocks in practice on `api.razorpay.com/v1/payouts`; the dashboard-merchant surface runs enforced (`shadow_mode=false`) (21 §1.3, §2.4, §4). AuthZ's own `prod.toml` `watchResourceGroups` **excludes `x_platform`** while stage/bvt/dev-serve include it — a second, independent candidate explanation (besides the `non_lms` org-string question) for "policies seeded but not enforcing" in prod (21 §3.3).

### Workflow Service (`razorpay/workflows`, finding 23 §A)
Fully accessible: Go, Twirp API (`WorkflowAPI`/`ActionAPI`/`ConfigAPI`/`CommentAPI`), Uber Cadence as the actual state-machine engine (every approval is a live Cadence workflow execution), MySQL for audit-trail bookkeeping only. Config templates compile a caller's simple range/steps/roles JSON into a full Cadence state graph. **No Passport, no AuthZ call, anywhere** in the approve/reject path — WFS trusts caller-supplied `actor_property_key/value` fields unconditionally, re-validated only against the pending state's own stored rules (string-equality, not an independent role lookup). Callback delivery is a genuine Cadence Activity (durable retry: 2s→×5.0 backoff→capped 1h→30-day expiration), HTTP Basic Auth, resolved via a static `[clients.<name>]` config table (not service discovery). Expiry is bounded purely by Cadence's `ExecutionStartToCloseTimeout` (config field `WorkflowExpireTime` hours; min ~4 months if set at all; defaults to 10 years) and **no code path fires any callback on expiry** — a Cadence timeout leaves WFS's own DB row at `status="initiated"` forever with PS never notified. `enable_approval_via_oauth` does not exist anywhere in WFS. WFS has **zero bulk RPCs** — repo-wide grep for "bulk" returns nothing.

### Batch service (`razorpay/batch`, finding 23 §B)
Java/Spring Boot, 7 k8s deployments sharing one Postgres DB, JSON-config-driven "batch types" (`payout.json`, `payout_approval.json`, six `v2/payouts_*_bene_*` types, `payout_link_bulk*.json`). Confirms Batch's `payout_approval` batch type calls `POST payouts/bulk_approve` **directly on Payouts Service, bypassing WFS entirely** — matching WFS's own confirmed absence of a bulk RPC. `payout.json` (the classic, primary bulk-create flow) derives its idempotency key as `"batch_" + BatchEntry.id` with **no Redis mutex, no cross-attempt coordination** — a materially weaker mechanism than the SHA1-hash + `RedisMutexLock(300s)` + 24h-cache scheme used by the newer sibling batch types calling the *same* `payouts/bulk` endpoint. The repo's own `core/AGENTS.md` claim of a "distributed mutex in BatchCore" is **not backed by any code** (grep-confirmed absent) — flagged as stale documentation. Batch does **not** poll `GET /v1/payouts?batch_id=...` — the call to `payouts/bulk` is synchronous, so Batch already has each row's outcome from the HTTP response itself; the caller (dashboard/monolith) instead polls Batch's own `GET /batch/{id}`.

### Stork (`razorpay/stork`, finding 25 §A)
Full Twirp contract (`WebhookAPI/ProcessEvent`), exact request shape payouts sends, exponential backoff (`factor=5, maxTime=86400s, maxAttempt=15`, extended per-owner schedule to 72h/23 attempts), HMAC-SHA256 signature over the raw payload (`X-Razorpay-Signature`), and **confirmed no dedupe anywhere** (`messages.event_id` has no unique constraint, zero `dedup*`/`idempoten*` hits) — at-least-once delivery per channel, no ordering guarantee (standard non-FIFO SQS p0/p1/p2). No caller of `WebhookAPI/Create` (merchant webhook registration) exists in the `payouts` repo — presumably lives in the monolith, unconfirmed.

### Mozart (`razorpay/mozart`, finding 25 §B)
Static routing map `namespace/gateway/version/action → config`; FTS's 8 named operations (`login`, `gateway_auth/session`, `transfer_init/status`, `beneficiary_verify/register`, `account_balance`, `create_otp`). Response envelope carries **no `meta`/processed/failed flags on the wire** — FTS computes them locally post-hoc from `bank_status_code` via two Go lookup maps (~140-entry `defaultErrorCodes` + `transferErrorCodes` transfer_init overrides). **Mozart ships a first-class built-in mock mode** (`mozart -mock`), running the identical route/auth/config pipeline as prod against canned fixtures — hundreds already exist under `app/testdata/fts/**`. IDFC has **no plain NEFT/IMPS gateway in Mozart's `fts` namespace** — only `idfc_upi` v1 exists.

### DCS / Splitz / Governor / Shield (finding 26)
DCS: gRPC + grpc-gateway/JSON (not Twirp), `KVService.{Get,Put,Patch,Evaluate,GetAuditHistory,GetEntityAggregate}`, key = `namespace/entity/entity_id/domain/object_name`, value = raw marshalled protobuf bytes. Storage is **DynamoDB primary + Aurora MySQL secondary** (legacy proxy-v1 table + proxy-v2 dual-write mirror), full local docker-compose e2e recipe available (DynamoDB-local + MySQL + Kafka). All requested payout-relevant proto fields (`Workflows`, `FundTransfer`, `ApiInterface`, `Cfa`, `direct_accounts.Configs/PayoutModeConfig`) resolved field-by-field with proto3 zero-value defaults. Splitz: real Twirp contract (`EvaluateAPI/{Evaluate,EvaluateBulk,FetchDecisionContext}`), deterministic MurmurHash bucketing (seeds 113/919), in-memory BigCache client-side eval (no Redis) — but **all 8 target experiment IDs/names are absent from every cloned repo**; experiment definitions live exclusively in Splitz's own MySQL, admin-managed at runtime (architectural, not an access gap). Governor: `POST /v1/namespaces/:id/execute`, govaluate-expression rule engine, returns boolean+score selections only (not fee amounts); Payouts configures 5 separate rule chains (basic/product/bank/mode/amount-range). Charge Collections holds the actual fee numbers (`Rule.percent_rate/fixed_rate/min_fee/max_fee`); the vendored `charge-collections-sdk` itself remains unreadable (go module cache outside sandbox). Shield: `shield-sdk` fully readable — **three actions exist: `allow`, `block`, `review`**; Payouts' integration only branches on `"block"` — `review` is currently indistinguishable from `allow` in Payouts' behavior, confirmed at the call site.

### Recon / RKG / UPS / devstack (finding 27)
Recon = "ART," Python/Flask + Spark/EMR, primarily a **batch data-lake reader**, not a live DB/API reader of payouts/FTS. Its write path is real and live: a human (FinOps) reviews and re-uploads an "RX Workflow" file via Admin Dashboard → recon turns rows into Kafka messages → `recon-workflow-kafka-consumer` fires a fully generic, config-driven HTTP request against `{FTS, API, PRS}` → FTS's own route table confirms recon (`ARTAuth` Basic credential) is directly authorized on `v1/attempts/:action` (PATCH/POST) and `v1/attempts/reconcile` (PUT), which cascades to transfer/payout status via FTS's normal attempt-update mechanism. Knowledge-base's RKG payouts bundle (143 nodes/232 edges, PR #157) exists, is cross-referenced against `PAYOUTS_SERVICE_GRAPH.json` with no factual contradictions and several complementary gaps identified in both directions (e.g. our graph is missing an `fts→x-account-statements` retry-preprocessor edge; RKG is missing the reverse `fts→payouts` health/downtime-callback edge). UPS (`payments-upi`) exposes the VPA mapper Payouts actually calls (`POST /v1/payments/validate/account`, Basic Auth + `X-Origin: payouts`); FTS does **not** call UPS directly — it calls the monolith's own `/v1/payment/validate/vpa`. `devstack` is confirmed to be generic internal-cluster DevX tooling with zero payments-domain content — does not solve the test-merchant/mock-gateway gap.

### kube-manifests / Spinnaker / alerts (findings 22, 22b)
`cde/` (not `prod/`) is the real prod-equivalent environment for payouts, cfa, validx, mozart. Payouts's `/v1/cron/*` is **not a k8s CronJob** — a Traefik `IngressRoute` + `Middleware` IP-whitelists the external **FastCron SaaS**, which is the sole owner of per-endpoint cadence (not in any repo). Payouts' "queued/scheduled/on_hold" timing is **not cron-driven at all** — ~25 permanently-running SQS/Kafka worker Deployments do continuous queue-draining. Real k8s `CronJob` resources exist only for ledger, cfa, batch, and stork; ledger's two CronJob templates hardcode `suspend: true` in every environment with no visible un-suspend mechanism in-repo. No `NetworkPolicy`, no sidecars, for any of the 15 profiled services; secrets are plain k8s `Secret`s populated from a DynamoDB-backed secret store, not Vault, for the 5 core services. The `alert-rules` repo, initially reported inaccessible by the first pass through this lane, **is** accessible (root-agent addendum 22b) — aggregate alerts exist for FTS webhook update failures and stuck payouts (thresholds >10/>50 failures per 15 min by status; stuck-payout alerts scoped to IDFC/IMPS channel and xpayroll source only, no generic "initiated too long" alert).

## (b) Previous assumptions that were WRONG

**W1 — Passport `authType` claim.**
Old: an earlier working draft assumed the JWT payload carries an `authType`/`auth_flow` field a local passport-minter could copy in.
Corrected: no such claim exists in the JWT at all. `auth_type`/`auth_flow` is Kong-internal request context (`common.lua:500-517`), used for routing/metrics, never serialized into the passport payload — confirmed independently in both the Kong-side implementation and the `goutils/passport` claim struct.
Evidence: `edge/kong-plugins/kong-plugin-upstream-jwt/kong/plugins/upstream-jwt/access.lua:86-205` (finding 21 §2); `goutils/passport/passport.go` claim struct (finding 24 §1).

**W2 — ValidX serves the public FAV route.**
Old: an early inference (predating this delta) had ValidX itself fielding `POST /v1/fund_accounts/validations`.
Corrected (reconfirmed with harder evidence this pass): the monolith owns that public route (`FundAccountValidationController@create`, `private`/`admin` auth groups) and calls ValidX only via its own internal routes. ValidX has no public surface.
Evidence: `app/Http/Route.php:3965-3972` (finding 20 §1); cross-checked against ValidX's own route list (finding 27, prior pass).

**W3 — A FAV-freshness gate exists on payout creation.**
Old: the closure catalog carried this as an open item (C29) with the gate's location unknown, and some flow narratives implied a create-time check.
Corrected: exhaustive grep of `Payout\Core`/`Service`/`Validator`/`Processor` for `fund_account_validation`/`FundAccountValidation`/`is_validated`/`validated_at` returns exactly one hit, and it is an **admin bulk-status-update** tool (marking a FAV record failed), not a create-time gate. No inbound call from the Payout module into `FundAccountValidation\Service` exists anywhere.
Evidence: finding 20 §6 (full grep result and read of the one hit).

**W4 — Monolith `payouts` table is simply deleted / simply present.**
Old: two conflicting framings coexisted — the client-side inference that the table is dropped (so monolith code paths referencing it are dead), versus the code-level finding that the table schema is present and actively read/written.
Corrected (per root-agent reconciliation): **both are true in different places.** The code (`Payout\Service::approveFundAccountPayout`, `ApprovedPayoutProcessor` job, `payoutUpdateByBASRecon`, `updatePayoutStatusManuallyInBatch`, the dual-write handler) still actively targets the local `payouts` table with no dead-code markers. Slack (#potential_outages, 2026-09-03) confirms the **physical table is absent in prod**, and `ApprovedPayoutProcessor` is failing right now with `Table 'api.payouts' doesn't exist`. An environment substitute of the monolith must implement these handlers and can choose whether to reproduce the failure or paper over it, but must not assume the code doesn't try.
Evidence: finding 20 §2, §8 (code); catalog C42 / Slack #potential_outages 2026-09-03 (prod state).

**W5 — Workflow Service enforces a bounded pending-approval expiry (hours/months auto-reject).**
Old: `PAYOUTS_FLOW_CATALOG.md` Flow C noted "docs: pending >3 months auto-rejected (owner unknown, likely WFS/monolith)" as a working hypothesis for where pending-payout expiry lives.
Corrected: WFS's only expiry mechanism is Cadence's `ExecutionStartToCloseTimeout`, set from `Meta.WorkflowExpireTime` hours — if unset, defaults to **10 years** (effectively never); if set, the *minimum* configurable value is ~4 months. Critically, **no code anywhere in WFS reacts to a Cadence timeout** (`grep "NewTimer"` → zero hits) — no reject callback fires, WFS's own DB row is simply left `status="initiated"` forever, and PS is never told. The 3-month auto-reject mechanism that does exist (`payouts_auto_cancel_on_expiry`, monolith Service.php:2530) is a **separate, monolith-side** cron unrelated to WFS's workflow-level expiry.
Evidence: finding 23 §A.8 (WFS); finding 20 §5 (separate monolith 3-month cron, for contrast).

**W6 — Kong rate-limits payout traffic (e.g. ~110 rps).**
Old: `CONTROL_AND_INVARIANT_CATALOG.md` C2 stated "rate limits 110 rps" as part of Kong's identity-minting control.
Corrected: **no `rate-limiting` plugin is wired to any payouts/payout-links/fund_accounts/contacts route anywhere** across `terraform-kong` and `edge`. The plugin exists generically in the Kong plugin catalogue but is not attached to any relevant surface — the "110 rps" figure has no basis in either repo.
Evidence: finding 21 §4 (full grep across both repos).

**W7 — `/payouts_service/dual_write` direction.**
Old: an earlier draft of this document (per finding 20's own note) had the dual-write moving payout business data *into* Payouts Service's database, or was otherwise ambiguous on direction — the client-facing framing of "the deleted table breaks dual-write" implied writes into the (now-gone) local table were simply failing outright.
Corrected: reading `app/Models/Payout/DualWrite/Payout.php` end-to-end shows the actual payout-row write is **PS → monolith's own local `payouts` table** (PS is read as authoritative source, upserted into the local shadow copy via an explicit local-connection `setConnection` + forced local-DB fetch). Only a small bookkeeping watermark (`payout_meta_temporary`) is written into PS's own database. The mechanism is queue-backed with 5 retries and, as *code*, shows no built-in error state — the failure mode is entirely a consequence of W4/C42 (physical table now absent in prod).
Evidence: finding 20 §8, `app/Models/Payout/DualWrite/Payout.php:24-71`, `Base.php:36`.

**W8 — `alert-rules` repo is inaccessible / FTS webhook-failure alert coverage is unknown.**
