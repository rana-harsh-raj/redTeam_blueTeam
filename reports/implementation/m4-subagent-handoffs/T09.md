## 3. What `provision_direct_merchant(campaign_id, role="direct", opening=10_000_000, channel="rbl")` creates

Ids (`ids_for_direct`): `num = 80000000 + sha256(campaign|role|direct) % 9000000` → merchant `ARENAD%08d` (Shared uses `ARENAM9xxxxxxx`, so the ranges never meet); balance `ARENADB%07d`, banking account `ARENADA…`, counter `ARENADC…`, fund-account row `ARENADF…`, fa id `ARENADX…`, bank account `ARENADK…`, contact `ARENADO…`, feature `ARENADT…`, BASD `ARENADS…`, hash_lookup `ARENADH…`, apidb banking account `ARENADM…`, purpose `ARENADP…`, ledger `ARD%07dAC%02d/DT%02d` — all ≤14 chars (asserted); FTS int id `910000 + num % 90000` (disjoint from generator `900001..900400`, asserted); own current-account number `2323` + 12 digits. A fail-closed guard (`_refuse_foreign_id`) refuses an id already present in kong's `merchants.json` under a foreign `secret_file`. Pricing plan id reserved via `reserve_plan_id` before any write.

## 8. Deviations / substitutions introduced (and contradictions found)

- **D1 (x-balances status)**: fresh rows use `status='active'` (what x-balances code matches). The M2 fixture row is `'activated'` (T04 C1) — left untouched. Both still work for `GET /v1/balances/{id}` (no status filter); the create precondition resolved through the x-balances GET for the fresh merchants (observed) and the BASD row is present as the fallback. **Contradiction logged**: seed `'activated'` vs code `'active'`.
- **D2 (FTS `source_accounts.account_type` casing)**: fresh rows use lowercase `'direct'` (T05). The M2 seed uses `'DIRECT'`. Runtime proof: with `'direct'` the attempts were processed by `rbl::direct::imps::*` workers (`fts_worker_route_observed`). **Contradiction logged** against `seeds/s4/fts.sql:52` (M2 row not changed). Whether M2's `'DIRECT'` attempts run on the pool `rbl::imps` queue instead is still unobserved (T05 unresolved 1).
- **D3 (reservation terminal hook does not fire in the twin under the monolith relay route)**: no payouts container has ever logged `INFLIGHT_RESERVATION_MARKED_AWAITING_BALANCE_REFRESH` / `…_RELEASED`; after `processed`/`failed` the item stays `live` until the reconciler (`/v1/cron/process_inflight_reservation_reconciliation`, cron-driver every 300 s) rebuilds it from the DB (`rebuilt=1/reclaimed=1` in `INFLIGHT_RESERVATION_RECONCILIATION_COMPLETED`), respecting a 60 s grace for young items. `prove_direct_merchant` therefore waits ≤ ~10 s for the hook, then waits out the grace window and runs one reconciler pass; the proof records `reservation_transition_source` (`terminal_hook` | `reconciler_pass` | `unsettled`) — it was `reconciler_pass` for every payout. Most likely cause: the PATCH `/v1/payouts/update_payouts_with_fts` path used by the monolith relay does not hydrate `MerchantConfig`, so `handleReservationOnTransition` skips (T04 §4 hook L70-72); the PS-direct webhook route (V13, `inject_transfer_webhook`) does. Not a provisioning defect; hand to the route/reconciliation owner (T06/T08) to confirm from `payout_internal_routes.go` and decide whether route E fidelity or the twin is at fault.
- **D4 (ledger topology)**: 6 rows (M2's FTS-current pair **and** the Shared 4-sub-account set at balance 0) rather than M2's 2. Neither is consulted by the Direct flow (0 journals); recorded so nobody reads the 4 merchant sub-accounts as "funded". Drop the 4 rows if strict M2 parity is preferred (one list in `provision_direct_merchant`).
- **D5 (monolith banking-account lookups)**: monolith-stub exposes **no** `GET /v1/banking_accounts/{account_number}/{merchant_id}` or `/v1/banking_accounts_balance_id/{id}` (T02 item 2); PS in the twin reads its pre-seeded `payouts.banking_accounts` row + x-balances. The self-check covers the x-balances HTTP read and the seed's `account_type/fts id` instead. The apidb `banking_accounts` row is written for parity only.
- **D6 (DCS)**: dcs-stub is registered through the seed file + restart (persistent) rather than `kv/put` (volatile). Note payouts never calls dcs-stub in this arena (dcs-stub logs show only `/health`; goutils/dcs ignores `ServerURL`, see `dcs-stub/server.py` docstring) — the `in_flight_reservation_enabled` decision at create time came from the monolith merchant-config `feature` list (`INFLIGHT_GATE_DECISION decision=reserved` logged by payouts-api). DCS registration is parity-only in the twin.
- **D7 (splitz)**: no write endpoint → seed copy of M2's variants + `docker restart splitz-stub` (documented in T07 row 22). Restart side effects (in-memory state loss in monolith-stub/dcs-stub/splitz-stub/bankingaccounts-stub; brief kong blip) are unchanged from the Shared recipe plus three more stubs — do not run mid-campaign.
- **D8 (stork secret)**: the fresh merchant's stork secret is the sink's fallback `arena_test_secret_min5` (M1–M3 use per-merchant secrets loaded by the sink at boot). Signature validation still `true`.
- **D9 (FTS parity_only tables)**: `source_account_mappings`, `account_type_mappings`, `preferred_routing_weights` are seeded but not read on the Direct branch (T05); step names carry `(parity_only)`.
