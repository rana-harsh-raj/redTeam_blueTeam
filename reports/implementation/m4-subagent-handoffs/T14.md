## H-D3 observation (raw request/response) — candidate, routed to autonomous replay

`GET /v1/payouts/free_payout/{balance_id}` performs `GetBankingAccountByBalanceID(ctx, balanceId)` with **no merchant scope** (`freePayout/core.go`, `bankingAccount/core.go:391`; controller passes only `request.BalanceID`). Runtime, as M1 (`rzp_live_ARENAM00000001`):

- own control `free_payout/ARENABAL000001` → **200** `{"free_payouts_consumed":0,"free_payouts_supported_modes":["IMPS","NEFT","RTGS","UPI","IFT"],"free_payouts_count":0}`
- **cross-tenant** `free_payout/ARENABAL000002` (M2's balance) → **200**, identical body — i.e. the endpoint resolves and returns config for a balance M1 does not own, where the scoped `GET /v1/payouts/pout_<M2>` returns 400 "id does not exist" (contrast asserted in G46).
- malformed `free_payout/NOTABALANCE` → **400** BalanceID length validation.

The test is `@pytest.mark.xfail(strict=False, reason="candidate H-D3 — for autonomous replay")`; it asserts the *desired-secure* invariant (non-owned balance → 400/404), which the runtime violates, so it registers as **xfail**, never a green pass. **Nuance for the judge:** in the current seed the two balances' free-payout configs are identical (both default zeros), so no *distinguishing* value leaks today — but the missing ownership check is real and would leak once the configs diverge (consumed count / supported modes / channel). Fixture caveat: `ARENABAL000002` exists in `banking_accounts` (verified). Recommend the autonomous loop seed a divergent free-payout config on M2 and replay.

Also surfaced (recorded, not a hard finding) — **H-D4 fidelity gap:** creating a payout as A that quotes B's `fund_account_id` succeeds (200) and binds the payout to **A** drawing **A's** balance (never B's). Source expects a 400 (`GetCfaFundAccountWithCache(ctx, fa, merchantID)`), but the arena CFA substitute resolves fund accounts without a merchant filter. Tenant isolation of money/state is intact (payout is A's, B untouched); this is a beneficiary-enumeration/substitute-fidelity nuance. G46 records it as candidate `H-D4` and asserts only the money-safety invariant.

## Design notes / decisions
- **Merchant-edge client vs. `ps_public_client`.** Boundary tests must observe the *edge* minting identity, so they authenticate with the raw merchant API key (Basic `rzp_live_<mid>:secret`) to kong-lite. Secrets are mounted read-only at `/run/m4` by the runner (never baked into the image, never in the compose `secrets:` list).
- **Fixture overrides, conftest untouched.** conftest's `merchant_m1/2` index the generated per-node `scenario-index.json`; the M4 node names aren't in it, so `helpers/m4_boundary.py` provides baseline-bound overrides + a `make_isolated_scenario` autouse (bank scenario set/cleared like conftest's) that each module imports.
- **State-unchanged control excludes `payout_status_counts`.** The arena's async workers advance a merchant's *own* held payouts (created→initiated) mid-test; that churn is the victim's own processing, not a cross-tenant effect. The victim invariant is asserted on the specific seeded row (settled to `initiated` first) plus banking-account + ledger/x-balances balance + total payout count.
- **G34 `updated_at`.** A duplicate terminal webhook re-touches `updated_at` (row re-saved) deterministically; this is **documented** in the trace, not asserted. The asserted G34/G45 invariant is status-stable + no new transition log + exactly one merchant delivery.
