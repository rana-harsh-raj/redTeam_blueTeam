## 7. Unresolved questions (needs follow-up / another pass)

1. **Real production hosts** for most outbound clients besides FTS (confirmed `fts-live.razorpay.com`) were not individually verified in `config/prod.toml` — dev/default.toml often points at a local monolith stub (`0.0.0.0:28080`) which is not informative about prod topology. Recommend a targeted `grep -A20 '^\[<service>\]' config/prod.toml` pass if exact prod endpoints matter.
2. **Actual Kafka topic name** consumed by the `fts` consumer task was not found as a literal string in config — likely resolved by the underlying Kafka SDK/library from `consumer_task.name` combined with an environment-specific topic-naming convention; not confirmed from source alone.
3. **`ExperimentForFtsRequestFromPayoutsService`** — name strongly implies a migration flag for "who calls FTS: monolith or Payouts Service", but its read-sites were not traced in this pass (grep found only the config field, not usage). Worth a dedicated grep of `SplitzExperimentList.ExperimentForFtsRequestFromPayoutsService` usage.
4. **WDA (`pkg/wda`) purpose** — client exists and is wired (`GetWdaClient`), config points to `wda-service.concierge.stage.razorpay.in`, but the actual call sites/purpose (workflow-dashboard-admin? something else) were not traced.
5. **`source_updater` job semantics** vs the HTTP `/retry/source_update` route — confirmed both exist but the exact relationship (is the HTTP route a manual trigger for the same underlying SNS push, or a different code path) wasn't fully traced.
6. **Ambiguity/timeout handling for FTS transfers** (e.g., what happens if FTS never responds/UTR is ambiguous) — `transfer_init_create.go` and `multi_account_route_selection.go` were read only at the request-construction level; response-side ambiguity handling (e.g., "processing" vs definitively failed) needs a deeper read of `internal/app/payouts/core.go`'s `HandlePayoutStatusUpdateViaFTS`.
7. **Velocity/limits checks** beyond Shield and Governor (fee rules) were not conclusively found as a separate "velocity check" service — Shield's `TriggeredRules` may encompass velocity, but this wasn't confirmed by reading Shield rule definitions (which live outside this repo, in `shield-sdk`/Shield service itself).
8. **CronJob schedules (actual cadence)** are not present in this repo at all (no K8s manifests found) — confirmed absence, but the schedule source-of-truth (devspace.yaml/infra repo) was not located.
