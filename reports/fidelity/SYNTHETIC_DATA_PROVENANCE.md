# Synthetic Data Provenance — RazorpayX Payouts Twin

Companion to `TWIN_SPEC/synthetic-data-model.yaml` (the authoritative data model). This file answers,
per record family: **where the shape came from**, **what is EXACT vs REPRESENTATIVE vs ASSUMED**,
**which twin seed files currently deviate**, and **the minimal external artifact that would raise an
ASSUMED item to EXACT**. Synthesized from `reports/fidelity/raw/{00..12}_*.md`,
`TWIN_SPEC/schema/*.sql|*.json`, and `ENV2_COMPOSE/seeds/{s4,monolith,dcs,splitz}/*`.

## How to read the tiers

- **EXACT** — field name/type/enum confirmed directly in a migration, proto, DTO, or validator.
- **REPRESENTATIVE** — table/endpoint identity confirmed, but the full column list or the specific
  values chosen are a documented, deliberate simplification (not a guess).
- **ASSUMED** — no source found; the reason is stated so the gap is visible, not silently papered over.

## 2. Confirmed cross-service identity facts (worth restating outside the YAML)

1. **`payouts.payouts` is one production table**, not two. The API monolith's own `payouts` table
   (`api/app/Constants/Table.php:31`) and the payouts-service's `payouts` table
   (`payouts/internal/app/payouts/model.go:168`) are the **same string**, reached by the monolith over a
   second `payout_service_database` connection (`api/database/Connection.php:37`). The `ps_*`-prefixed
   tables are CI-only test scaffolding, per an explicit doc-comment in
   `2022_07_01_095954_create_ps_payouts.php:12-14`: *"This table doesn't exist on prod. It only exists on
   CI."* A twin seeding a `ps_payout_details` shadow table instead of reaching the real
   `payout_details`/`payouts` tables over a second connection is **not production-faithful**.
2. **`beneficiary_bank_code` asymmetry is permanent, by design.** Present in payouts-service's own
   `payout_details` (out-of-band column, no migration ever added it, confirmed via full commit history);
   explicitly `unset()` before every dual-write into the monolith's `payouts_details`
   (`DualWrite/PayoutDetails.php:10-13,63-64`, comment: *"present only in Payouts Service's payout_details
   not in API Monolith"*). Do not "fix" this asymmetry in a twin.
3. **`fts_fund_account_id` is the join key across four services with four different physical types**:
   `payouts.banking_accounts.fts_fund_account_id` (CHAR(14) string), `fts.fund_accounts.id` (INT
   AUTO_INCREMENT), `x-balances.balance.fts_fund_account_id` (VARCHAR(255) string),
   `ledger.account_details.entities.fts_fund_account_id` (jsonb array element, string). All four must
   agree as strings.

## 6. Mechanism gaps that no amount of seed data fixes

Two items in the data model are **unreachable regardless of seed content** until a mechanism (not data)
fix lands — flagged here so they aren't mistaken for seeding tasks:

1. **Splitz client-side eval** (`FetchDecisionContext`) always returns an empty experiment list for
   payouts; `splitz.experiment_assignment` seed data has zero effect on payouts until this is fixed to
   return real `Experiment{...}` objects, or scenarios are routed through server-side `Evaluate` instead.
   (L10 §B.2)
2. **Workflows Service (WFS) is entirely MISSING** from the twin. `payouts.workflow_config` /
   `workflow_state_map` seed rows are inert without a WFS substitute that accepts `WorkflowAPI.Create` /
   `ActionAPI.Create` calls and fires the real callback contract (`POST /v1/workflow/state`,
   `.../payouts_internal/{id}/approve|reject`). (L08)
