## B. Edge / auth

- **Dashboard GET routes are being migrated off the API monolith** via a payouts-owned Kong shadow service + upstream-override into the Payouts Service, with a "shadow-gateway framework" comparing legs before honoring the PS response (Faisal Rafiq Ahanger, #tech_infra_edge, 2026-08-28, full thread read). PRs: terraform-kong #10860, #10954, #10960/10965 (templates), #10967 (base/api cleanup), #10987 (authz-enforcer + upstream-jwt parity), #10991, #11033, #11047.
- **"Identification-only passport" issue** (terraform-kong PR #10991, Faisal Rafiq Ahanger, 2026-08-28): "while testing shadow mode on devstack we found that dashboard-proxy traffic reaches the Payouts Service with an identification-only passport. basic-auth-x maps these requests to the anonymous consumer, so upstream-jwt mints authenticated=false, and today the monolith completes authentication inline" — i.e. today the API monolith does the real dashboard-user authentication step; if Edge routes straight to Payouts Service, that authentication step must move somewhere else (resolved per below: the monolith's `authenticate` endpoint is still called per-request even for diverted routes, preserving `merchant_users` binding verification).
- **Full audit of middleware parity required for cutover** (thread `p1787909324386769` in #platform_spine_edge_oncall / cross-posted #tech_infra_edge, read in full):
  1. IP restriction (`ip-restriction-x`, dashboard-proxy `merchants.dashboard_whitelisted_ips_live`) — resolved: monolith's `authenticate` endpoint still runs the IP filter per request on diverted routes (X-Dashboard-Ip forwarded), so nothing waits on an Edge-native build.
  2. Rate limiting — resolved: both rate-limiter plugins are global on Kong; per-route rules mirrored (110 rps on `route_name *`) before divert.
  3. Merchant-activation check — open/roadmap: `authz-enforcer`'s native `merchant_activation_check` doesn't cover dashboard-proxy traffic (skips non-public/private auth flows); Payouts Service is building this itself via account-service regardless.
  4. Membership attestation — resolved: passport's user-consumer + impersonation claims do **not** by themselves attest user-to-merchant membership, but the monolith's `authenticate` call validates `merchant_users` binding on user-auth routes before marking context authenticated; this coverage is preserved for diverted routes.
  5. Merchant-level cohorting at Kong for dashboard routes — a schema whitelist gap: `upstream-override`'s ctx matcher can already read `proxy.consumer_id` / `impersonation.consumer.username` at runtime (dotted-path traversal in `common.lua`), but the config-time schema (`schema.lua:212`, `common.lua:660-666`) only whitelists `{rzp_mode, authenticated, identified, consumer_id}` — `impersonation.consumer.username` needs adding to enable per-merchant divert control at Kong itself (previously worked around by diverting the whole route and choosing merchants inside the Payouts Service via Splitz). Confirmed by a Slash code-trace in the same thread (razorpay/edge, kong-plugin-user-auth, kong-plugin-consumer-identifier, kong-utils).
  6. Service-side enforcement: `goutils/authz` — the SDK that syncs policies from Consul per watched resource group and enforces locally from passport claims — is confirmed as "exactly the supported pattern" for a non-Edge service to consume authz policies directly.
- **authz PR #2577** (razorpay/authz): a self-serve gateway-group policy CSV adding **14 policies granting GET on `/v1/payouts/schedule/timeslots`** for the standard X dashboard roles — the pilot route for the whole cutover effort. #x-payouts-reliability, Faisal Rafiq Ahanger, 2026-08-31. A related self-serve seeding issue: their first Policy Creator V3 run used one policy name per role instead of one policy per (service, resource, action) with roles mapped in — needed a cleanup run only spine-edge could trigger (#platform_spine_edge_oncall, 2026-08-31). A parallel finding: policies seeded under `100000razorpay::banking::non_lms` don't enforce even though the enforcer logs show correct role evaluation — open question whether `banking::non_lms` org is actually consulted for merchant-dashboard traffic that resolves to "banking" product, or if enforcement only works under the "pg" org today (unresolved as of 2026-08-31 EOD).
- **Maker-checker / roles more broadly**: separate from payouts-specific authz work, #x-production-issues (Risheek Ravi, 2026-06-16 and Lokesh B M, 2026-06-03) show banking roles (`finance_l1/l2/l3`, `view_only`) under `orgId=razorpayx` sometimes lack child role mappings in AuthZ, and a `CAC_LOCATE_ROLE_USING_EXPERIMENT` migration caused 403s for `operations`/`finance`/`support` CAC granular roles on X dashboard traffic — an ongoing authz/CAC migration risk area for payouts approval UI.

## C. Ledger

- **Two separate ledger integration modes exist and payouts touches at least one of them**: "CLS" (Centralized/Central Ledger System, aka "PG Ledger Reverse Shadow") is the API-monolith↔`razorpay/ledger` integration for PG-side balance/credit tracking, with **Shadow mode** (`pg_ledger_journal_writes`: API DB is source of truth, ledger gets async writes) and **Reverse Shadow mode** (`pg_ledger_reverse_shadow`: ledger becomes source of truth, API writes blocked/redirected) — #payments_core, Satyanand Prasad, 2026-04-17; #ace-team Slash summary, 2026-08-03. This is PG-side; RX/Payouts ledger usage is evidenced separately via `payout_initiated`/`payout_processed` transactor events (see below) but the docs found don't explicitly name a distinct "RX Ledger" vs PG Ledger split — treat as **open question** whether payouts uses the same `ledger` service/cluster under a different tenant, or a dedicated instance. Confidence: medium.
- **Transactor events for payouts**: `payout_initiated`, `payout_processed` seen directly in a merchant debugging thread — #cross-border-slash, Shah Jay, 2026-08-06: "for pout_TJgPghJmEYyEsH payout I can see payout_initiated transactor event for which journal created but not seeing payout_processed event in journal entry on ledger even though payout is already processed." IRCTC-specific events: `irctc_payout_processed` (#platform-ledger-alerts, Nishant Dayal, config missing in PG tenant for reverse-shadow — 2026-03-20) and `irctc_payout_initiated`/`irctc_payout_processed` in the FTS→Catalyst posting flow (#api_decomposition, Sarfaraz Nawaz, 2026-08-29). Confidence: high.
- **Reversal ledger handling**: reversal creation in the API monolith (`Core::updatePayoutStatusManually()` → `handlePayoutReversedBase()`) creates the reversal entity **first**, then attempts ledger journal creation — meaning a ledger failure (e.g. `ACCOUNT_DISCOVERY_ACCOUNT_NOT_FOUND` from a wrong `fund_account_id`) can leave a reversal recorded with **no corresponding credit to the merchant**, requiring manual replay by the ledger team once given the correct `fts_fund_account_id`/`fts_account_type`. Multiple live incidents in #x-production-issues (Priyanka Marabille, 2026-07-30, 2026-08-03/04) show this is a known, recurring manual-recovery pattern; a bug ticket was raised to fix the ordering. #x-production-issues, Priyanka Marabille, 2026-08-03 explicitly notes: "in the normal reversal flow, the system verifies that the ledger transaction is created successfully before creating the reversal entity" but the **manual force_update admin action path skips this validation** — a known gap. Confidence: high.
- **fts_fund_account_id mapping**: a live bank-channel misrouting incident (#x-production-issues, Nikhil Reddy, 2026-09-03) shows the master balance_id mapped to `fts_fund_account_id` 505907866, which on FTS is (incorrectly) mapped to the ICICI channel when the account/IFSC actually belong to Axis — i.e. FTS holds an independent fund-account→bank-channel mapping keyed by `fts_fund_account_id` that can drift from the actual account metadata (sourced from `sub_balance` table in `prod_x_balances`), and this mapping must be manually corrected on the FTS side. Confidence: high (concrete IDs and root cause given).
- **No specific payouts+ledger P0 incident this week beyond the reversal-journal-failure pattern was found**, aside from ledger-wide incidents (`ART_LAG` alerts, PG↔Ledger 401 auth failures on 2026-08-24/09-02) that are not payouts-specific.

## D. FTS

- **Status propagation mechanism**: FTS updates its own Transfer/Attempt state from bank polling, then sends a **status webhook** to either (a) the **API monolith** (`/v1/update_fts_fund_transfer`, "legacy"/default path — historically also updates the FTA/Fund Transfer Attempt record) or (b) **directly to the Payouts Service** (`UpdateFtsFundTransfer` endpoint), controlled by a Splitz experiment `CreateTransferMetaRollout` keyed on `origin_service == "payouts"`. This is **not** Kafka-based for the terminal status callback to Payouts/API — it is a synchronous HTTP webhook call from FTS. (Kafka/CDC *is* used for the Catalyst/Ledger outbox posting side of IRCTC, a separate pipeline.) Fully reconstructed via code trace by Slash in #x-techsupport thread (Priyanka Marabille, 2026-07-15, read in full) — cites `fts/internal/transfer/service.go:1070/1147/1330`, `payouts/internal/app/payouts/core.go:2099`.
- **Known failure mode #1 — "FTS terminal / Payouts stuck in processing"**: this is the dominant, repeatedly-cataloged incident pattern across dozens of #x-production-issues tickets (PSE "Issue 4 — FTS Status Update Not Reaching Payout Service" and "Issue 1 — Payout Stuck in processing, FTS/attempt stuck at CREATED"). Root causes seen across tickets: (a) webhook delivery failure from FTS to Payouts specifically for reversed cases (Bharath B Yalaburgi, 2026-07-15: "known issue... for some of the reversed cases there is a webhook failure from FTS to Payouts... Rajesh is already working on fixing them"); (b) `MERCHANT_MAPPING_RULE_NOT_FOUND` in FTS (missing source-account mapping) — surfaces as failure never propagating; (c) no FTA (Fund Transfer Attempt) entry created even though FTS shows processed — a large batch of TAM merchants affected, "0 SR" reported (Bharath B Yalaburgi, 2026-08-31); (d) today's live incident, `pout_TVcGW8Kil6WIjj`, stuck in Processing/`internal_status: initiated` for >3 days while FTS shows Failed — the exact scenario named in this task's context, actively worked 2026-09-03 16:57–17:27 IST. Confidence: high (very high volume of corroborating tickets).
- **Known failure mode #2 — UTR mismatch / not propagated**, root-caused and fixed live (full thread read, #x-techsupport, thread ts 1783665757.295279): three compounding bugs — (1) FTS's `GetMapFromTransfer()` builds the webhook body from the `Transfer.Utr` field (not the latest `Attempt.Utr`), racing against the DB commit of the attempt→transfer UTR copy; (2) Payouts Service `core.go:2099` had a **write-once UTR guard** (`if payoutInitialUTR == "" && request.Utr != ""`) that silently dropped legitimate UTR corrections once any UTR was set; (3) a `LimitedWebhookFlowExperiment` in FTS suppresses UTR-only webhooks entirely for IMPS/UPI when enabled. Fix shipped as **`razorpay/payouts#1872`** (Slash-authored, 2026-06-30-ish per thread) changing the guard to `request.Utr != "" && payoutInitialUTR != request.Utr` and adding a new trace event `PAYOUT_UTR_UPDATED_FROM_TRANSFER_STATUS_WEBHOOK`.
- **Ordering violation**: FTA is updated before the webhook fires to Payouts in the "legacy" path; in the direct-to-Payouts path this FTA update step is skipped entirely (dropped, not moved) — a structural regression flagged as one of the root causes of both the UTR bug and general status-sync gaps.
- **Bank channels seen in evidence**: RBL, Axis, ICICI, Yes Bank (YBL/YBL_XAS), IDFC, SLICE — all appear as live payout/settlement channels with channel-specific quirks (e.g. RBL Mozart parsing crash on missing `ENTRY_AMOUNT_ARRAY` field for a "no transaction record" reply — #payments_nbplus, Rituraj Paul, 2026-09-03; YBL_XAS statement reconciliation lag T+2 vs T+1 for peer channels — #rx-recon, Bharath B Yalaburgi, 2026-08-07).
- **Mozart's role**: gateway/bank integration layer for verify/status-check calls (used for balance polling too — x-balances calls Mozart to poll bank balance for Direct/CA accounts, not a Razorpay-maintained ledger: "the balance for Direct accounts comes from Mozart polling the bank (Axis), not from a Razorpay-maintained ledger. x-balances is a read-only mirror" — #x-production-issues, Chethan Kumar N M, 2026-07-13). Mozart also handles the bank verify/status-check protocol parsing for FTS/payments (per-gateway config, e.g. RBL crash above).
- **Recon service's role**: a separate `recon` service does ART (Auto Reconciliation Tool?) reconciliation, and is explicitly distinguished from Payouts — a bank-statement/internal-report/X-Payouts three-way match handled by the "recon owner" (currently partly manual, being automated on top of the existing ART product — #engage-product, Vaibhav Tandon, 2026-08-13). Recon is not indexed in HyperDx per a Slash log-search note (#x-production-issues, 2026-09-03), making live debugging harder.
- **XAS (x-account-statements) role**: ingests bank statements per channel (RBL/Axis/ICICI/IDFC/YBL/SLICE) and is used both for account-statement display and as an input to 3-way ART reconciliation (statement leg vs. payout leg vs. main_statement leg). XAS degradation/ingestion failures (`STATEMENT_NOT_FOUND`, missing UTR extraction for IDFC, tagging under wrong Internal/External bucket) are a recurring root cause of "unreconciled" payouts and of the "Status Mismatch Cases Direct" bucket (up to 842 cases in one incident, #rx-payouts, Slash, 2026-04-30). XAS also enriches account-statement rows by matching payouts to statement lines; payouts stuck non-terminal never get an XAS source event (#rx-recon, Slash RCA, 2026-08-10).

## E. Webhooks

- Merchant-facing `payout.*` webhooks (`payout.updated`, `payout.processed`) are sent **from the Payouts Service to Stork**, which is the actual delivery system to merchant endpoints (#x-production-issues, Himanshu Tekchandani, 2026-06-09, with Coralogix log links for both). This differs from the FTS→Payouts internal status webhook (D above) — Payouts is itself both a webhook *consumer* (from FTS) and a webhook *producer* (to Stork for merchants).
- **Known issue — out-of-order webhook delivery**: `payout.processed` was observed sent ~100ms before `payout.updated`, and Stork has no epoch/millisecond ordering check, so it delivered them out of order (#x-production-issues, Bharath B Yalaburgi, 2026-06-09, asked Stork to enforce ordering by epoch time). Razorpay's public docs already describe this as expected/tolerated behavior and instruct merchants to treat `processed`/`reversed` as terminal and ignore anything arriving after (#meesho, Akshay Kadam, 2026-06-30) — i.e. the fix request may not have been accepted; ordering guarantees are explicitly *not* promised.
- Onboarding a new Stork webhook historically required a `razorpay/api` PR + AFD approval; a team asked for a current SOP given the decomposition (#tech_infra_stork, Gowtham N K B, 2026-06-15) — suggests webhook *registration* process itself may still run through API-monolith-adjacent tooling even as delivery is on Stork. No definitive answer found on new SOP.

## F. Approval workflow

- Payouts approval/maker-checker ("workflow") logic is evaluated **inside the Payouts Go service itself**, not a separate workflow microservice and not (any longer) purely in the API monolith — confirmed by log evidence: `WORKFLOW_CREATE_PAYOUT_FLOW` / `IsWorkflowApplicable` trace events emitted by the Payouts Service (#x-production-issues, Priyanka Marabille, 2026-09-03, trace_id-referenced). Config for whether workflow applies is read from **DCS** (`payout_workflows`, `enable_payout_workflow`, `skip_approval_workflow_for_api`, `skip_workflow_for_dashboard`, `skip_workflow_for_payroll`, `enable_approval_via_oauth`).
- **Feature-flag semantics** (multiple concrete examples): `skip_workflow_for_api` / `skip_approval_workflow_for_api` applies only to payouts created directly via the merchant's own Payouts API key/secret ("strict private auth") — does **not** apply to payouts created by internal apps (e.g. XPayroll) using their own credentials, which instead need `skip_wf_for_payroll` (#x-production-issues, Priyanka Marabille, 2026-08-10). A separate `Batch service` sits in front of bulk approvals and can itself fail (`BATCH_SERVICE_PAYOUT_APPROVAL_BULK_RESPONSE` errors from Workflow evaluation) causing partial-batch approval failures (#x-production-issues, Abhay Nataraj, 2026-06-22).
- **Recurring bug class — "cache/propagation" of `payout_workflows` config**: several *separate* incident tickets (2026-06-18, 07-15, 07-24, 08-08, 08-10, 08-27) all match the same signature — payouts bypass the configured approval workflow because a cache/propagation bug in the Payouts Service + DCS causes `payout_workflows` to be ignored intermittently, even when `skip_approval_workflow_for_api` is correctly unset. This looks like a systemic, still-recurring defect as of early September 2026, not a one-off. Confidence: high (many independent, near-identical tickets over 3 months).
- OTP: approval workflow is meant to require OTP verification for the approving user before a payout transitions past pending; at least one incident shows a bypass "after OTP verification" traced to the DCS feature simply being absent for the merchant (not an OTP-flow bug per se) — #x-production-issues, 2026-07-15.

## G. Queue-if-low-balance and balance source

- **Balance source is bifurcated by merchant migration state**: for merchants still on the legacy monolith Balance path, x-balances is a **read-only mirror** of whatever balance Mozart polls from the bank (for Direct/CA accounts against Axis) — there is no Razorpay-maintained reservation ledger in that path (#x-production-issues, Chethan Kumar N M, 2026-07-13, "fundamental problem that will impact all high TPS merchants"). For merchants on the **Payouts Service (PSE, `payout_service_enabled: 1`)**, the **ledger balance (via x-balances) is the sole authoritative source** for payout decisions — two separate balance stores exist and only one is authoritative depending on migration state (#x-production-issues, Slash, 2026-06-25).
- **Queue mechanism**: a payout with `queue_if_low_balance=true` moves to `Queued` state when the internal (ledger) balance check fails; a **cron in the Payouts Service** periodically re-scans queued payouts and reprocesses only those whose merchant balance was updated within the last 6 hours (to avoid repeatedly re-failing on stale balance) — #x-ledger-integration, Sonal Shailja, 2026-07-10. Additional queue reasons beyond low balance: `fee_recovery_pending` (#x-integrations, Chethan Kumar N M, 2026-08-04).
- **Race condition / no in-flight reservation (known, being fixed)**: the low-balance gate is "a plain amount > balance check with no reservation," so concurrent bulk approvals can all read the same balance snapshot and all pass, over-committing the balance (#x-production-issues, Manchikanti Rajesh, 2026-06-30; Akshay Kadam MoM, 2026-07-13, on the "Moneylicious"/bulk-payout incident). An in-flight balance reservation mechanism was deployed the week of 2026-08-29 but introduced a new bug: reservations held too long for long-running pending payouts (e.g. IMPS Deemed Success) reduce available balance and cause unnecessary re-queuing (Akshay Kadam, 2026-08-29) — actively being tuned as of early September.
- A per-merchant **Balance Threshold** feature ("queue proactively before hitting bank-side low-balance failures") was launched 2026-01-19 (#prod-bulletin, Angad Singh) to reduce arbitrage between RZPX-side and bank-side balance views.
- `x-balances` explicitly named as the service owning balance polling/storage, with per-bank dedicated worker pods (e.g. `x-balances-worker-idfc-balance-fetch-*`), 30-min polling rotation for non-priority merchants (#x-production-issues, Prashant Upadhyay, 2026-08-10).

## H. Bulk payouts / Batch service decomposition ("Batch Edge Routes")

- Batch service (`razorpay/batch` presumably) has **completed its own API decomposition**, but several dashboard owners — explicitly including the **Payouts team** — have not yet moved their dashboards from proxying through the API monolith to calling the new **"Batch Edge Routes"** directly (#api_decomposition, Ankit Choudhary, 2026-08-10, 2026-08-20). As of 2026-08-20, Payouts dashboard batch CRUD (`batch_fetch_multiple` polling alone ~44–53k/mo) still hits the API monolith even though DB reads are proxy-merged from Batch service (0 DB QPS on monolith side).
- Batch service processes bulk payout uploads with per-row async processing, queues, row-level fault tolerance (#product-support-engineering, Jaskaran Singh, 2026-08-25, describing the general Batch pattern).
- Known Batch+Payouts bug class: bulk batches split across pods can race on idempotency keys; the losing pod's retry hits a non-retriable 400 "Duplicate Idempotency Key" instead of succeeding, causing merchant-visible spurious failures for payouts that actually succeeded — recurring issue (4th occurrence noted 2026-05-14; also seen 2026-05-25).
- Explicit routing-flow discussion for the cutover (#x-payouts-reliability, Faisal Rafiq Ahanger, 2026-06-22): "For payouts the request flows is Edge -> API -> Payouts. If we move the proxy layer to Payouts Service the flow becomes Edge -> Payouts(proxy) -> API -> Payouts" — i.e. the team explicitly weighed keeping a thin proxy inside the Payouts Service vs. Edge routing directly, given Kong's `upstream-override` cannot rewrite the request path.

## I. Testing / dev environments

- **DevStack / e2e-test-orchestrator** is the standard E2E harness; a "Test Data Manager" / merchant-pool-based provisioning system underlies it (`/v1/testdata/merchant?variant_name=...&service=...&count=1`), which acquires pooled pre-created merchants per "variant" rather than creating on demand — on-demand creation was still an open ask as of 2026-07-17 (#testdata_management_service, Jonnalagaddaa Venkata Srihari).
- **Payout Service has automated E2E coverage in ITF**, running on every PR against master, exercising the real **payouts → FTS → Mozart → mock-gateway** chain (#x-payouts-reliability, Preetham M R, 2026-08-06). Coverage listed: Create (existing fund account/BA, composite BA, NEFT, standard VA/shared account), Fetch (multiple payouts, ...).
- Devstack reliability is an ongoing pain point: daily issue-scan reports in #platform-devstack show recurring merchant-pool "degraded" states blocking E2E runs (e.g. UPI mandate merchants, 2026-08-27/28), DB secret refresh gaps post DevStack V2 migration, and a new "Devstack Failure Classifier" tool launched 2026-09-02 to triage these automatically.
- Payouts-specific live E2E failure today: "Payouts E2E's failing, there is no webhook being received from FTS to Payouts. So the status check after 60 retries getting failed" (#x-payouts-reliability, Nikhil Reddy, 2026-09-03 06:03) — i.e. the same FTS→Payouts webhook gap seen in prod also breaks the E2E suite.
- **Test mode**: payouts can be created with test API keys but no real fund movement occurs; test-mode payouts remain in `Processing` by default and merchants must use specific actions/API calls to simulate other terminal outcomes (#x-integrations, Anuj Dwivedi, 2026-07-28). No dedicated "bank simulator" service for payouts specifically was found (contrast with card/UPI payments, which have a rich mock-gateway/simulator ecosystem) — Gift City team explicitly notes "we do not have a dedicated mocking environment" and relies on bank sandbox (2026-08-31), suggesting payouts bank-simulation tooling is thin. Confidence: medium (absence of evidence).
- **Getting a test merchant**: no single documented self-serve flow was found in these searches beyond the pooled `/v1/testdata/merchant` endpoint (internal, per-service) and generic onboarding via Admin dashboard bulk-submerchant creation. Treat as an open question requiring a direct ask in #platform-devstack or #x-payouts-reliability.
