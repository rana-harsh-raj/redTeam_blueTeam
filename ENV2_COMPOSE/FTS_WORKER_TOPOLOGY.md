## 2. How each worker was mapped

* **Production `-command` argument** — every `fts-live-worker-*-deployment.yaml` runs the same image with
  `args: ["worker", "<worker_name>"]` (e.g. `kube-manifests/templates/fts/templates/`
  `fts-live-worker-rbl-direct-upi-initiate-transfer-deployment.yaml:47-49`). The twin passes the identical
  string through the binary flag the arena image exposes: `-command=<worker_name>`, matching the 13
  pre-existing blocks.
* **Queue** — `[queue.worker_queue_map]` in `config/templates/base/fts/env.default.toml:106-289`, which is
  **byte-identical** to the FTS clone's `fts/config/env.default.toml` (verified with `diff`). The LHS is the
  `-command` value, the RHS is the single machinery queue that process consumes.
* **Fallback rule (why an unmapped key is dangerous)** — `env.default.toml:113`: *"If the mapping for the
  supplied worker name does not exist, then the worker will listen on the `DEFAULT_QUEUE` as defined above"*,
  and `env.arena.toml:61` sets `DEFAULT_QUEUE = "default"`. An unmapped worker therefore does not fail
  loudly — it becomes a *second consumer of the `default` queue* and steals work from `fts-worker-default`.
* **Arena config overlay** — `config/templates/base/fts/env.arena.toml` overrides only hosts/ports inside
  `[queue]`; it does not define `[queue.worker_queue_map]`, so all 155 mapped keys are inherited from
  `env.default.toml` unchanged. **No config change was needed for any of the 13 added workers.**

### 3.1 Honest caveat: added ≠ exercised

All 13 boot, connect to `mysql-fts` + `redis` and block on their own machinery queue, which is what makes the
*topology* complete. Traffic is a separate axis: `seeds/generated/s4/fts.sql:57-69` seeds
`channel_information_status` / `source_account_mappings` for **channel RBL, `mozart_identifier` v1, modes
IMPS + NEFT only**. So today:

* fed by the arena's own payout flow: `hv::fire_transfer_status_webhook`, `hv::initiate_transfer`,
  `slow_lane::initiate_transfer`, `rbl::direct::initiate_transfer`, `rbl::direct::check_transfer_status`,
  `rbl::direct::imps::hv::initiate_transfer`, `rbl::direct::slow_lane::initiate_transfer` — reachable as soon as a
  payout picks the high-value / slow-lane / direct branch;
* **idle until a UPI seed exists**: the four `rbl::upi::*` and two `rbl::direct::upi::*` workers. Their queue-map
  keys and `[integration.api.rbl…]` config are real and present; what is missing is a `channel_information_status`
  row with `mode='UPI'`. That is a seeding lane's call, not a compose gap, and it is recorded per-worker in
  `fts-worker-gaps.json` only for the workers that were *not* added.

`mozart-sim` is **not** a blocker for any of them: `substitutes/mozart-sim/server.py:496-506` splits the path into
`{namespace}/{gateway}/{version}/{action}` and dispatches on `{action}` alone, ignoring the gateway and version
segments, so `rbl/v5`, `icici/v1` etc. all reach the same handlers.

## 4. Deferred: `rbl::v5::initiate_transfer` and `rbl::v5::check_transfer_status` (2 of the 15 P0)

**Not added. Exact missing dependency: the `[queue.worker_queue_map]` entry for these two commands does not
exist in any cloned repo.**

| evidence | what it shows |
| --- | --- |
| `kube-manifests/templates/fts/templates/fts-live-worker-rbl-v5-initiate-transfer-deployment.yaml:47-49` | prod really runs `args: [worker, rbl::v5::initiate_transfer]` |
| `kube-manifests/prod/fts/values.yaml:383-384` | `replicas: 1` for both — genuinely live in production |
| `config/templates/base/fts/env.default.toml:106-289` | 155 worker-map keys; **no `rbl::v5::*` key** (`grep` returns 0) |
| `fts/config/env.default.toml` (clone) | byte-identical to the twin copy — the key is missing upstream too, not lost in the copy |
| `config/templates/base/fts/env.default.toml:113` | unmapped `-command` silently falls back to `DEFAULT_QUEUE` |
| `config/templates/base/fts/env.arena.toml:61` | `DEFAULT_QUEUE = "default"` in the arena |
| `.../fts-live-worker-rbl-v5-initiate-transfer-deployment.yaml:100-102,118-119` | the pod mounts ConfigMap `fts-app-config`, which is **referenced by every fts Deployment and defined nowhere in `kube-manifests`** — the real mapping lives in that out-of-band config source |
| `config/templates/base/fts/env.default.toml:1826-1990` (clone `fts/config/env.default.toml:1826+`) | `[integration.api.rbl.v5.*]` gateway config *does* exist — the gap is exactly and only the queue name |

Adding them anyway would have been a **regression**, not a gain: with no map entry both processes would join the
`default` queue and start stealing tasks from `fts-worker-default`. Inventing `rbl_v5_initiate_transfer` /
`rbl_v5_check_transfer_status` by naming convention is not a *pure copy of a real default/prod value* — the lane
rule for touching `env.arena.toml` — so `env.arena.toml` was left untouched.

**To unblock:** obtain the two `worker_name = "queue_name"` lines from the `fts-app-config` ConfigMap (the
external fts config source that k8s mounts at `/config/`), add them to `env.arena.toml`'s
`[queue.worker_queue_map]` with a `file:line` citation, then add the two compose blocks in the §3 shape.
